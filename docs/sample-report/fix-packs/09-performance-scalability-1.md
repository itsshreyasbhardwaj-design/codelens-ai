**What is wrong.** The pool is constructed once per process at src/lib/db.ts:5 and no size option (`max`, `connectionLimit`, `poolSize`, `connection_limit` or the driver's equivalent) is set, so the number of connections this process will hold is whatever the driver defaults to. ### 5. SCALE-002 — POST /api/upload stores uploaded files on the instance's local filesystem

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: scalability
- **Files**: `src/app/api/upload/route.ts`, `Dockerfile`
- **References**: The Twelve-Factor App — VI. Processes (stateless, share-nothing processes); The Twelve-Factor App — IX. Disposability; CWE-400 Uncontrolled Resource Consumption

**What is wrong.** The handler writes the uploaded file into the local 'uploads' directory of the process that served the request, and returns a path under that directory as the file's location. That makes the write instance-local while the read is expected to work from anywhere. With a single long-lived instance and a persistent disk this behaves correctly, which is why it survives development. With more than one instance, a file written by one instance is simply absent from the others, and the request that reads it back fails depending on where it lands. Where the deployment unit is an image or a serverless function, the filesystem is recreated on every deploy and may be read-only or ephemeral, so the file can disappear without any scaling at all. A second effect belongs to the same write: the upload is materialised fully in memory before it is written, so concurrent uploads consume memory in proportion to their combined size with no ceiling in the code.

**Why it matters to a user.** Uploaded files are intermittently missing. A user uploads a file, sees it succeed, and then gets a broken image or a 404 when the page that displays it is served by a different instance — or after the next deploy. The failure is not reproducible on demand, which usually means it is reported as "sometimes my images disappear" and never diagnosed.

**Likely root cause.** Writing to the local filesystem is the shortest path to a working upload endpoint, and it keeps working until there is a second instance or a redeploy.

**Evidence.**
- `src/app/api/upload/route.ts:13`
  ```
  await writeFile(`./public/uploads/${file.name}`, buffer);
  ```
  written to a path inside the running instance's own filesystem ('uploads')
- `src/app/api/upload/route.ts:14`
  ```

  ```
  the same path is handed back to the client as the location of the stored file
- `Dockerfile:1`
  ```
  FROM node:20
  ```
  the deployment unit is an image whose filesystem is recreated on each deploy, so files written at request time do not survive it

**Traced relationship** (call):
1. `src/app/api/upload/route.ts:13` (`POST`) — writeFile() writes the uploaded file under 'uploads' on the local filesystem
2. `src/app/api/upload/route.ts:9` (`POST`) — the handler returns that same path to the client, so the file is expected to be readable later
3. `Dockerfile` — the application is packaged as a container image, so that filesystem is per instance and is recreated on deploy

**Consequences to keep in mind while fixing.**
- Backups of the database do not contain these files, so a restore produces records pointing at files that no longer exist.
- Serving user-uploaded files from the application's own static directory also puts them inside the application's origin, which has security consequences beyond scaling.
- Horizontal scaling becomes a data-loss event rather than a capacity change.

**Recommended remediation.** Write the file to a storage service every instance shares — object storage (S3, GCS, R2, Azure Blob) or a mounted network volume — and persist only the resulting key in the database. Prefer streaming the request body straight to that store, or issuing the client a pre-signed upload URL so the file never passes through the application process at all; either removes the in-memory buffering as well. Serve the file back through the store's own URL or a signed redirect rather than from the application's static directory. If local storage must be kept for now, attach a persistent volume, pin the deployment to a single instance, and state that constraint in the deployment configuration.

### 6. SCALE-004 — Outbound calls in the request path have no timeout (1 call site)

- **Severity**: medium
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: scalability
- **Files**: `src/app/api/upload/route.ts`
- **References**: Google SRE Book — Addressing Cascading Failures; CWE-400 Uncontrolled Resource Consumption; OWASP API Security Top 10 — API4:2023 Unrestricted Resource Consumption

**What is wrong.** An awaited outbound call in a server request handler sets no timeout and no abort signal, and no timeout is configured on the client or anywhere in the enclosing module. How long the request waits is therefore decided by the upstream service. A dependency that fails by returning an error is harmless; a dependency that fails by answering slowly holds one of this application's request slots, one connection, and one set of buffers for as long as it chooses to take. With enough concurrency, all of the slots end up held, and the application stops serving requests that have nothing to do with the slow dependency. How much concurrency that takes depends on the runtime's limits and the real traffic, so this finding needs runtime verification to quantify: what is determinable from the source is that nothing bounds the wait. Note that the platform's default `fetch` has no timeout at all, so the absence of a signal here means the absence of any limit.

**Why it matters to a user.** When an external dependency slows down, users do not get a quick error — they get a page that never finishes loading. Shortly after, parts of the application that do not use that dependency stop responding too, because the slow calls have consumed the capacity to serve anything. From outside it looks like the whole application is down, and it stays that way until the dependency recovers.

**Likely root cause.** No timeout is the default in most HTTP clients, so omitting one is easy to do and invisible until a dependency degrades rather than fails.

**Evidence.**
- `src/app/api/upload/route.ts:23`
  ```
  const res = await fetch(url);
  ```
  fetch() is awaited in PUT /api/upload with no timeout or abort signal, so the response time of this request is bounded by the upstream, not by us

**Consequences to keep in mind while fixing.**
- Held request slots mean one slow dependency takes down endpoints that never call it, which is the standard shape of a cascading failure.
- Without a deadline there is nothing for a retry or a circuit breaker to key off, so neither can be added usefully later.
- Load balancer and platform timeouts fire first and return a generic error, which hides which dependency was responsible.

**Recommended remediation.** Give every outbound call an explicit deadline. With `fetch`, pass `signal: AbortSignal.timeout(ms)`; with a client library, set its timeout option at construction so it applies to every call and cannot be forgotten at a new call site. Choose the value from the budget for the whole request rather than per call, and propagate the remaining budget to calls made further down. Treat the timeout as a real outcome: decide for each call whether to fail the request, serve degraded content, or fall back to a cached value. Where a dependency is not needed to answer the user, move it out of the request path entirely.

**Estimated effort.** small

### 7. COST-003 — prisma.user.findMany() fetches User relation 'orders' that the handler never reads

### 8. SCALE-003 — POST /api/webhooks/stripe applies several writes with no transaction on an at-least-once delivery path

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: scalability
- **Files**: `src/app/api/webhooks/stripe/route.ts`, `prisma/schema.prisma`
- **References**: CWE-362 Concurrent Execution using Shared Resource with Improper Synchronization; Enterprise Integration Patterns — Idempotent Receiver; CWE-367 Time-of-check Time-of-use Race Condition

**What is wrong.** The handler performs 2 separate persisted writes (prisma.order.update, prisma.webhookEvent.create) with no transaction around them and no condition that would make a repeated application a no-op. This endpoint is a provider callback, and callback delivery is at-least-once by design: providers retry on timeout, on a non-2xx response, and sometimes simply twice. Two deliveries of the same event can therefore be in this handler at the same time, on the same or on different instances. Because the writes are independent statements, the two executions interleave freely: both can apply the state change, and the sequence can stop between the first write and the last, leaving the record changed and the rest of the work undone. There is a record kept of the delivery (prisma.webhookEvent.create), but it is written after the state change, so it documents what happened rather than preventing it; and no unique constraint on that store exists to reject a duplicate in any case. No read, conditional update, or upsert guards the first write.

**Why it matters to a user.** A duplicate delivery applies the same change twice. Where the change is a state transition on a payment or an order, the user can be shown a state that was reached by a retry rather than by the event that was actually final — for example a cancelled or failed transaction left showing as completed — and a partial run leaves the record changed with the follow-up work missing. These cases are rare per request and routine at volume, and they tend to surface as support tickets about money rather than as errors in logs.

**Likely root cause.** The writes were added in the order the work happens, which reads correctly as a sequence. Nothing in local testing executes the handler twice at once.

**Evidence.**
- `src/app/api/webhooks/stripe/route.ts:17`
  ```
  await prisma.order.update({
  ```
  first persisted write (prisma.order.update), applied before anything establishes that this delivery is new
- `src/app/api/webhooks/stripe/route.ts:22`
  ```
  await prisma.webhookEvent.create({ data: { eventId: event.id, type: event.type } });
  ```
  a further write (prisma.webhookEvent.create) in the same handler, outside any transaction
- `prisma/schema.prisma:14`
  ```
  model Order {
  ```
  the row being changed lives here; nothing in the handler constrains the change to a single application of it
