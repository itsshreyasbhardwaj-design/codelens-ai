### 1. SEC-007 — POST /api/login compares passwords without hashing

- **Severity**: critical
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/login/route.ts`
- **References**: OWASP A02:2021 Cryptographic Failures; CWE-256 Plaintext Storage of a Password

**What is wrong.** The handler compares a stored password value directly with the submitted one. No password hashing function (bcrypt, argon2, scrypt, or PBKDF2) appears in this handler, which means the stored value is the password itself. The comparison is also not constant-time, so it leaks information through timing.

**Why it matters to a user.** If the database is ever read by an attacker — through a backup, a log, an injection flaw, or an insider — every user's password is immediately usable, including on the other services where people reuse passwords.

**Likely root cause.** Authentication was built against a plaintext column during early development and never migrated.

**Evidence.**
- `src/app/api/login/route.ts:15`
  ```
  if (!user || user.password !== body.password) {
  ```
  stored value compared directly against the submitted password; no hashing function is used in this handler

**Consequences to keep in mind while fixing.**
- Migration requires a rehash-on-next-login path; existing stored values cannot be recovered into hashes.
- Password reuse means the breach extends beyond this application.

**Recommended remediation.** Store a hash produced by argon2id, scrypt, or bcrypt with a per-user salt, and verify with that library's constant-time compare. Migrate by adding a hash column, hashing on next successful login, and removing the plaintext column once no rows depend on it. Treat all existing passwords as compromised and require a reset.

**Estimated effort.** medium

### 2. SEC-011 — POST /api/login accepts unlimited authentication attempts

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/login/route.ts`
- **References**: OWASP A07:2021 Identification and Authentication Failures; CWE-307 Improper Restriction of Excessive Authentication Attempts

**What is wrong.** The POST /api/login handler performs no rate limiting, and no rate-limiting library or middleware was found in the project. Credential guessing is therefore bounded only by network throughput.

**Why it matters to a user.** Attackers can brute-force passwords and run credential-stuffing attacks against the login endpoint, compromising accounts whose passwords are weak or reused. Users may also be locked out or the service degraded by the attempt volume.

**Likely root cause.** Rate limiting is often deferred to infrastructure and then never configured.

**Evidence.**
- `src/app/api/login/route.ts:11`
  ```
  export async function POST(req: Request) {
  ```
  authentication handler with no rate limiting in its body, and no rate-limiting dependency anywhere in the project

**Consequences to keep in mind while fixing.**
- Password strength rules alone do not stop credential stuffing with breached passwords.
- Without limits there is no natural signal that an attack is in progress.

**Recommended remediation.** Apply a rate limit keyed on both client IP and the submitted account identifier, with exponential backoff or a temporary lockout after repeated failures. Enforce it server-side ahead of the credential check, log the rejections, and return a uniform error so the limiter does not itself leak which accounts exist.

**Estimated effort.** medium

### 3. SEC-019 — POST /api/login reveals whether an account exists

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/login/route.ts`
- **References**: OWASP A07:2021 Identification and Authentication Failures; CWE-204 Observable Response Discrepancy

**What is wrong.** The handler distinguishes "no such account" from "wrong password" in its response. That difference lets anyone test an email address and learn whether it is registered.

**Why it matters to a user.** An attacker can compile a list of valid customer email addresses, which enables targeted phishing and narrows a credential-stuffing attack to accounts that actually exist.

**Evidence.**
- `src/app/api/login/route.ts:11`
  ```
  export async function POST(req: Request) {
  ```
  the handler returns different messages for an unknown account and a wrong password

**Recommended remediation.** Return one identical message and status for both cases ("those credentials are not valid"). Keep the timing of both paths similar so the difference does not leak through response time, and record the specific reason in server logs only.

**Estimated effort.** trivial

### 4. SEC-003 — GET /api/orders/[id] reads a Order by request id without checking ownership

- **Severity**: critical
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/orders/[id]/route.ts`, `prisma/schema.prisma`
- **References**: OWASP A01:2021 Broken Access Control; CWE-639 Authorization Bypass Through User-Controlled Key; OWASP API Security Top 10: API1 Broken Object Level Authorization

**What is wrong.** The handler authenticates the caller but then loads a Order using the 'id' value from the request, without restricting the query to records the caller owns. Order has an ownership column ('userId'), and it is never compared with the session identity in this handler. Authentication answers "who is this"; this handler never answers "may they see this record".

**Why it matters to a user.** Any logged-in user can read or modify another user's Order records simply by changing the identifier in the URL. This is the most commonly exploited class of API flaw and requires no special tooling.

**Likely root cause.** The authentication check was added and mistaken for an authorisation check, which is a very common conflation.

**Evidence.**
- `src/app/api/orders/[id]/route.ts:11`
  ```
  export async function GET(req: Request, { params }: { params: { id: string } }) {
  ```
  session is resolved, so the caller is authenticated
- `src/app/api/orders/[id]/route.ts:15`
  ```
  const order = await prisma.order.findUnique({
  ```
  Order looked up by an identifier taken from the request (id)
- `prisma/schema.prisma`
  ```
  model Order { … userId … }
  ```
  the model has an ownership column 'userId' that this query does not filter on

**Traced relationship** (route_authorization):
1. `src/app/api/orders/[id]/route.ts:11` (`GET`) — authentication enforced: an unauthenticated caller is rejected
2. `src/app/api/orders/[id]/route.ts:15` (`GET`) — prisma.order.findUnique() keyed by request value 'id'
3. `prisma/schema.prisma` — Order.userId identifies the owning user
4. `src/app/api/orders/[id]/route.ts:15` — no comparison between userId and the session identity anywhere in the handler

**Consequences to keep in mind while fixing.**
- Every other handler that loads a Order by request id likely has the same gap.
- Sequential or guessable identifiers make enumeration trivial; opaque ids reduce but do not remove the exposure.

**Recommended remediation.** Scope the query to the caller: include 'userId' from the resolved session in the where clause (for example `where: { id, userId: session.userId }`) so a record belonging to someone else simply is not found. Where administrators must bypass this, branch on an explicit role check rather than widening the default query. Returning 404 rather than 403 for a record the caller does not own avoids confirming that it exists.

**Estimated effort.** small

### 5. SEC-002 — DELETE /api/orders/[id] performs no authentication check

- **Severity**: critical
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/orders/[id]/route.ts`
- **References**: OWASP A01:2021 Broken Access Control; CWE-306 Missing Authentication for Critical Function

**What is wrong.** The handler for DELETE /api/orders/[id] does not call any session or authentication helper, and no rejection path for an unauthenticated caller exists in its body. It queries: Order.

**Why it matters to a user.** An unauthenticated caller can change or destroy stored data.

**Likely root cause.** The route was added without the project's authentication helper, or enforcement was assumed to be global.

**Evidence.**
- `src/app/api/orders/[id]/route.ts:24`
  ```
  export async function DELETE(req: Request, { params }: { params: { id: string } }) {
  ```
  handler DELETE contains no authentication check

**Traced relationship** (route_authorization):
1. `src/app/api/orders/[id]/route.ts:24` (`DELETE`) — DELETE /api/orders/[id] handler declared
2. `src/app/api/orders/[id]/route.ts:24` (`DELETE`) — no call to a session or authentication helper in the handler body
3. `src/app/api/orders/[id]/route.ts` — handler queries the Order model

**Consequences to keep in mind while fixing.**
- Client-side route guards do not mitigate this: the endpoint is reachable directly.
- Rate limiting and logging will record the access as anonymous traffic.

**Recommended remediation.** Resolve the session at the top of the handler using the project's existing helper, return 401 when it is absent, and then apply the authorisation rule for the resource. Enforce this server-side in the handler (or in middleware that provably matches this path), not in the client.

**Estimated effort.** small
