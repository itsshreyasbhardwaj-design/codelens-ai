### 1. SEC-001 — SQL built by string interpolation and passed to pool.query()

- **Severity**: critical
- **Confidence**: CONFIRMED — the evidence is conclusive
- **Category**: security
- **Files**: `src/lib/db.ts`
- **References**: OWASP A03:2021 Injection; CWE-89 SQL Injection

**What is wrong.** The statement passed to pool.query() is assembled by interpolation rather than parameterised. Any value reaching that interpolation is executed as SQL, not treated as data.

**Why it matters to a user.** An attacker who controls the interpolated value can read, modify, or delete any data the database user can reach, including other customers' records, and in many configurations can escalate further.

**Likely root cause.** A query was written as a string because the value was assumed to be internal or already validated.

**Evidence.**
- `src/lib/db.ts:12`
  ```
  const sql = `SELECT * FROM "Product" WHERE name LIKE '%${term}%'`;
  ```
  untrusted value interpolated into query text
- `src/lib/db.ts:13`
  ```
  const result = await pool.query(sql);
  ```
  the built string is passed to pool.query()

**Traced relationship** (import):
1. `src/lib/db.ts:12` (`searchProductsRaw`) — query text assembled with interpolation
2. `src/lib/db.ts:13` (`searchProductsRaw`) — passed to pool.query() as statement text

**Consequences to keep in mind while fixing.**
- Input validation elsewhere does not fix this: the vulnerability is in how the statement is built.
- Database audit logs will show the injected statement as a legitimate application query.

**Recommended remediation.** Replace the interpolation with a parameterised query: pass values as bind parameters ($1/? placeholders or the ORM's tagged-template form such as Prisma's `$queryRaw` with template parameters) so the driver sends them separately from the statement text. Where an identifier (table or column name) genuinely must be dynamic, validate it against a fixed allowlist.

**Estimated effort.** small

### 2. SEC-008 — PUT /api/upload fetches a URL supplied in the request

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/upload/route.ts`
- **References**: OWASP A10:2021 Server-Side Request Forgery; CWE-918 Server-Side Request Forgery

**What is wrong.** The handler issues a server-side request to a URL taken from the request body or query. The server can usually reach addresses the caller cannot: cloud instance metadata endpoints, internal services, and localhost-bound admin interfaces.

**Why it matters to a user.** An attacker can make the server fetch internal addresses and return the response to them — on many cloud providers that includes the instance metadata service and therefore credentials. It also turns the server into a proxy for scanning the internal network.

**Likely root cause.** A feature that legitimately needs to fetch a remote resource was implemented without constraining where it may point.

**Evidence.**
- `src/app/api/upload/route.ts:23`
  ```
  const res = await fetch(url);
  ```
  the destination URL comes from request input and is fetched without validation

**Traced relationship** (import):
1. `src/app/api/upload/route.ts:21` (`PUT`) — PUT /api/upload reads a URL from the request
2. `src/app/api/upload/route.ts:23` (`PUT`) — fetch() is called with that value

**Consequences to keep in mind while fixing.**
- A blocklist of IP literals is not sufficient: DNS names, redirects, and alternative encodings bypass it.
- Returning the response body to the caller turns the flaw into a direct read of internal services.

**Recommended remediation.** Constrain the destination: require https, resolve the hostname and reject private, loopback, link-local, and metadata ranges (checking after DNS resolution, and again on every redirect), prefer an allowlist of permitted hosts, disable redirect following or re-validate each hop, set a timeout and response size cap, and do not return the raw upstream body to the caller. Where possible route such requests through an egress proxy that enforces these rules centrally.

**Estimated effort.** medium

### 3. SEC-013 — Unsanitised value rendered as HTML in <div>

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/products/page.tsx`
- **References**: OWASP A03:2021 Injection; CWE-79 Cross-site Scripting

**What is wrong.** A dynamic value is passed to dangerouslySetInnerHTML on <div>, which bypasses React's automatic escaping. If any part of that value originates from user input or from stored data that a user can influence, the markup it contains executes in the browser of whoever views the page.

**Why it matters to a user.** A visitor viewing this content can have script run in their session: their token can be stolen, actions can be performed as them, or the page can be rewritten to phish them. Stored content makes it persistent, affecting every viewer.

**Likely root cause.** Rich text or markdown needed to render as HTML and the value was passed through unsanitised.

**Evidence.**
- `src/app/products/page.tsx:18`
  ```
  <div dangerouslySetInnerHTML={{ __html: p.description }} />
  ```
  dangerouslySetInnerHTML receives a dynamic value with no sanitisation in this expression

**Consequences to keep in mind while fixing.**
- A Content-Security-Policy reduces but does not eliminate the impact.
- Already-stored values may contain payloads: existing data needs review as well as the code fix.

**Recommended remediation.** Render the value as text if it does not need to be HTML. If it must be HTML, sanitise it with a maintained sanitiser (DOMPurify or equivalent) using a strict allowlist of tags and attributes — ideally on write, server-side, so stored data is clean — and add a Content-Security-Policy that forbids inline script as defence in depth.

**Estimated effort.** small

### 4. SEC-012 — POST /api/upload accepts uploads unsafely (3 issues)

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/upload/route.ts`
- **References**: OWASP A04:2021 Insecure Design; CWE-434 Unrestricted Upload of File with Dangerous Type; CWE-22 Path Traversal

**What is wrong.** The upload handler has the following gaps: no content-type or extension allowlist; no size limit; the client-supplied filename is used to build the destination path. Because the destination path is built from the client-supplied filename, a name containing path separators or `..` writes outside the intended directory. Without a type allowlist, content that the web server will execute or that browsers will treat as active content can be stored and then served.

**Why it matters to a user.** An attacker can write a file to an arbitrary location the process can reach, which can overwrite application files or place executable content inside the served directory.

**Likely root cause.** Upload handling was written for the happy path with a trusted browser form in mind.

**Evidence.**
- `src/app/api/upload/route.ts:9`
  ```
  export async function POST(req: Request) {
  ```
  no content-type or extension allowlist; no size limit; the client-supplied filename is used to build the destination path

**Consequences to keep in mind while fixing.**
- Files stored now may already be hostile; existing contents need review, not just a code fix.
- A CDN or static route may serve stored files with a content type that makes them active.

**Recommended remediation.** Generate the stored filename server-side (a UUID plus an extension derived from a verified type) and never use the client-supplied name in a path. Enforce an explicit content-type allowlist validated against the file's actual bytes rather than the declared header, cap the size before buffering the whole file, store uploads outside the web root or in object storage, and serve them with `Content-Disposition: attachment` and a restrictive content type.

**Estimated effort.** medium
