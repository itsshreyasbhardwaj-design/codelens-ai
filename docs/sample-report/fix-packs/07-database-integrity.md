### 1. PERF-001 — Database query inside a for loop (N+1 against Order)

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: performance
- **Files**: `src/app/api/admin/stats/route.ts`
- **References**: CWE-1073 Non-SQL Invokable Control Element with Excessive Number of Data Resource Accesses; CWE-1050 Excessive Platform Resource Consumption within a Loop; docs/LIMITATIONS.md — this scan does not measure runtime behaviour

**What is wrong.** prisma.order.findMany() is issued inside a for loop, so the number of database round trips is 1 for the outer collection plus one more for every element it contains — 1 + N, where N is the size of that collection at run time. N is not known statically and this scan does not measure it, so no multiplier is stated here; what is certain from the syntax tree is that the count scales with the data rather than staying fixed. Because the call is awaited inside the loop, each round trip also waits for the previous one to finish, so the waiting accumulates on top of the query count. The collection being iterated is itself the result of a query with no row ceiling, so N here is the size of a table rather than a fixed batch. The same handler already loaded 'orders' through an include on an earlier query, so this loop re-fetches rows the process is already holding in memory.

**Why it matters to a user.** As the underlying collection grows, the page or endpoint takes progressively longer to respond and occupies a database connection throughout. Behaviour looks correct with a handful of seeded rows and degrades or times out at production volume, typically for the accounts with the most data — the heaviest users are hit first.

**Likely root cause.** The relation was added to an include for one purpose, and a later change fetched it again per row rather than reading the already-loaded field.

**Evidence.**
- `src/app/api/admin/stats/route.ts:18`
  ```
  const orders = await prisma.order.findMany({ where: { userId: user.id } });
  ```
  prisma.order.findMany() sits inside a for loop, so it runs once per element
- `src/app/api/admin/stats/route.ts:12`
  ```
  const users = await prisma.user.findMany({ include: { orders: true } });
  ```
  an earlier query in the same handler already fetched 'orders' for every row

**Consequences to keep in mind while fixing.**
- Connection-pool pressure: one slow request of this shape can hold a connection long enough to starve other requests.
- The cost is invisible in local testing, because it is proportional to the row count, not to the code path.
- Any further handler that loops over the same collection almost certainly repeats the pattern.

**Recommended remediation.** Read the already-fetched relation from the loaded rows instead of querying again — the include on the earlier query has the data. Where the included relation is not enough, replace the loop with a single query: fetch all the rows you need in one call filtered by an `in` list of the parent identifiers, or use the ORM's aggregation (for example a grouped count) so the database does the per-parent work. If the relation is only needed for a count, select the count rather than the rows.

### 2. PERF-002 — Order.userId is filtered on in queries but is not indexed

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: performance
- **Files**: `prisma/schema.prisma`, `src/app/api/admin/stats/route.ts`
- **References**: CWE-1049 Excessive Data Query Operations in a Large Data Table; CWE-405 Asymmetric Resource Consumption (Amplification); docs/LIMITATIONS.md — this scan does not measure runtime behaviour

**What is wrong.** Application code filters Order on 'userId' at 1 call site (src/app/api/admin/stats/route.ts:18), but the model declares no index that leads with that column — its declared indexes are [id]. Without one, the database has to examine rows it cannot rule out in advance, and the work for each of these queries grows with the size of the table rather than with the number of rows actually matched. One of these call sites is inside a loop, so the unindexed lookup is repeated per element. Whether the planner currently chooses a scan, and what that costs, depends on the deployed table size and statistics — neither is visible here.

**Why it matters to a user.** Requests that look up Order by 'userId' get slower as the table grows, in a way that is invisible on a small development data set. The accounts with the most data notice first, and because a scan holds resources for longer than a lookup, the slowdown spreads to unrelated requests sharing the same database.

**Likely root cause.** 'userId' was added as a plain column — commonly a foreign key, which several databases do not index automatically — and the query that filters on it was written later.

**Evidence.**
- `src/app/api/admin/stats/route.ts:18`
  ```
  const orders = await prisma.order.findMany({ where: { userId: user.id } });
  ```
  filters Order on 'userId'
- `prisma/schema.prisma:16`
  ```
  userId    String
  ```
  'userId' is declared here; the model's declared indexes are [id]

**Traced relationship** (data_policy):
1. `src/app/api/admin/stats/route.ts:18` (`GET`) — prisma.order.findMany() filters Order on 'userId' inside a loop
2. `prisma/schema.prisma:14` — Order is declared here
3. `prisma/schema.prisma:16` — 'userId' is a column of Order; declared indexes are [id], none of which lead with 'userId'

**Consequences to keep in mind while fixing.**
- Query planners may still choose a scan after the index exists if statistics are stale, so the index alone is not proof of a fix.
- Each added index costs write throughput and storage, so the set of indexes should match the queries that actually run, not every column.
- A composite index may serve this query better if it is always filtered alongside another column — check the real query shapes before adding a single-column index.

**Recommended remediation.** Add an index on Order.userId in the schema (for a Prisma schema, `@@index([userId])` on the model, or `@@unique` where the column is genuinely unique; in SQL, `CREATE INDEX` — concurrently on a live table so the migration does not hold a write lock). If this column is always filtered together with another, prefer one composite index with the most selective leading column over two single-column indexes. Then confirm the planner actually uses it, and remove indexes that no query needs so write cost does not creep up.

**Estimated effort.** small

### 4. PERF-004 — prisma.product.findMany() reads the Product table with no row limit

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: performance
- **Files**: `src/lib/db.ts`
- **References**: CWE-770 Allocation of Resources Without Limits or Throttling; CWE-1049 Excessive Data Query Operations in a Large Data Table; docs/LIMITATIONS.md — this scan does not measure runtime behaviour

**What is wrong.** prisma.product.findMany() is called without any row ceiling — no take, limit, first, or cursor argument. The query therefore returns however many rows the Product table currently holds, and every one of them is materialised in the application process. The row count is a property of the deployed data, not of the code, so this scan cannot say how many rows that is today or how fast it is growing.

**Why it matters to a user.** The process holds the entire table in memory for the duration of this call. As the table grows this shows up as rising memory use and slower requests across the whole instance, not only in this feature, because the memory and the database connection are shared.

**Likely root cause.** The query was written when the table was known to be small, and no ceiling was added because none was needed yet.

**Evidence.**
- `src/lib/db.ts:22`
  ```
  return prisma.product.findMany();
  ```
  no take/limit/cursor argument, so every matching row is returned

**Consequences to keep in mind while fixing.**
- Memory use for this request is proportional to the table size, so one call can affect every other request on the same instance.
- A retry or a concurrent duplicate of this call multiplies the memory cost.

**Recommended remediation.** Add an explicit ceiling to the query (take/limit, or LIMIT in raw SQL) and make it the default rather than an option. Where the whole set genuinely must be processed, stream or page through it in chunks (cursor-based batches) so memory stays constant regardless of the row count. Select only the columns actually used, so the per-row cost is bounded as well as the row count.

**Estimated effort.** small

### 6. PERF-006 — GET /api/admin/stats returns a whole collection with no pagination parameters

**What is wrong.** The handler for GET /api/admin/stats reads a collection from User, Order without a row ceiling, and the endpoint accepts no parameter a caller could use to ask for a bounded page: no limit, offset, cursor, or page input appears in the request contract or is read from the query string. **Why it matters to a user.** Every client of this endpoint — including the application's own pages — must download and parse the full collection on each call. The endpoint feels fine while the table is small and becomes a slow, heavy request that can time out as data accumulates, with mobile and low-bandwidth users affected first and worst.

**Likely root cause.** The endpoint was written to serve one screen that showed everything, and pagination was deferred until the data grew.

**Evidence.**
- `src/app/api/admin/stats/route.ts:11`
  ```

  ```
  GET /api/admin/stats handler: its request contract carries no limit, offset, cursor, or page input
- `src/app/api/admin/stats/route.ts:12`
  ```

  ```
  prisma.user.findMany() reads the collection with no row ceiling

**Consequences to keep in mind while fixing.**
- Clients written against the unpaginated shape will break when paging is added later, so the fix gets harder the longer it waits.
- Response size scales with the table, so caching layers and payload limits in front of this endpoint are harder to size.
- An unbounded read on a public or cheaply reachable endpoint is also an availability concern: repeated calls amplify load with no ceiling.

**Recommended remediation.** Add paging to the endpoint: a limit parameter with a conservative default and an enforced maximum, plus a cursor (preferred — it stays correct while rows are inserted) or an offset. Apply that limit to the query itself rather than slicing in the application, and return the paging state (next cursor, or total count where it is cheap) so clients can iterate. Keep the default response bounded even when the caller sends no parameters, and version or feature-flag the change if existing clients depend on receiving everything.

**Estimated effort.** medium
