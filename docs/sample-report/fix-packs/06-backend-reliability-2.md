**What is wrong.** SESSION_TTL_HOURS is read at src/lib/auth.ts:29, but .env.example — which this project uses to declare its required configuration — does not list it. The repository therefore describes a configuration surface narrower than the one the code depends on, and the only record of the variable is the line that reads it. **Likely root cause.** The variable was added to the code and to the deployed environment, but .env.example was not updated.

**Consequences to keep in mind while fixing.**

### 3. REL-009 — products page awaits data with no error or loading state

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: reliability
- **Files**: `src/app/products/page.tsx`
- **References**: CWE-755 Improper Handling of Exceptional Conditions; Next.js App Router: error and loading conventions

**What is wrong.** src/app/products/page.tsx awaits listAllProducts() while rendering, and the route segment it belongs to declares no error or loading boundary — no such file exists in this directory or in any ancestor up to the app root — and the module itself contains no try/catch and no Suspense boundary. In the App Router these files *are* the mechanism for the two states: without `error.tsx` a thrown error escapes to the nearest boundary above, and with none present the framework falls back to its own generic error screen; without `loading.tsx` or a Suspense boundary the segment has no fallback, so navigation waits for the data before anything renders.

**Why it matters to a user.** While the data loads the user sees nothing happen: the old page stays on screen or the browser simply appears to hang, with no indication that their navigation registered. On a slow connection this reads as an unresponsive application, and the usual response is to press the link again. If the query fails the user is dropped onto a generic framework error page with no explanation, no retry, and no way back into the product other than the browser's back button.

**Likely root cause.** The page was built against a fast, always-succeeding local database, where neither state is ever visible.

**Evidence.**
- `src/app/products/page.tsx:6`
  ```
  const products = await listAllProducts();
  ```
  listAllProducts() is awaited while rendering this page
- `src/app/products/page.tsx:3`
  ```
  export default async function ProductsPage() {
  ```
  no try/catch in this component, and no error/loading boundary file in this route segment or any ancestor up to app/

**Traced relationship** (import):
1. `src/app/products/page.tsx:6` — page awaits listAllProducts() during render
2. `src/app/products/page.tsx` — no error or loading boundary found in this segment or its ancestors

**Consequences to keep in mind while fixing.**
- A single failing query takes out the whole route segment rather than degrading one part of the page.
- Perceived performance is governed by the slowest query on the page, because nothing renders until it completes.

**Recommended remediation.** Add the boundary files the framework expects for this segment: an `error.tsx` that explains what failed and offers a retry (it receives a `reset` function for exactly that), and a `loading.tsx` — or a Suspense boundary around the slow part — so the shell renders immediately. Where only part of the page depends on slow data, wrap that part alone, so the rest is usable while it loads. Put a boundary at the app root as well, as the last line of defence for segments that have none.

**Estimated effort.** small

### 4. REL-012 — POST /api/chat performs I/O with no error handling

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: reliability
- **Files**: `src/app/api/chat/route.ts`
- **References**: CWE-391 Unchecked Error Condition; CWE-755 Improper Handling of Exceptional Conditions

**What is wrong.** POST /api/chat in src/app/api/chat/route.ts awaits I/O — a database call, a file write, or an external request — and the handler contains no try/catch and no rejection handler. When that I/O fails, and it will (a dropped connection, a constraint violation, a timeout, a provider incident), the rejection propagates out of the handler. The framework turns it into a generic 500 with no application-specific body, no structured log line identifying which operation failed, and no partial cleanup of anything the handler had already changed.

**Why it matters to a user.** The user gets an unexplained failure for something that may be entirely recoverable — a value that needs correcting, a duplicate that already exists, a dependency that is briefly unavailable. Because the response cannot distinguish those cases, the interface cannot tell the user whether to fix their input, retry, or wait, so the usual outcome is an abandoned task and a support request. For a write that partly completed, the user is left not knowing what state their data is in.

**Likely root cause.** The handler was written for the success path. Nothing in the type system or the build requires a failure path, and the framework's default 500 makes the omission invisible until it is examined.

**Evidence.**
- `src/app/api/chat/route.ts:14`
  ```
  export async function POST(req: Request) {
  ```
  POST /api/chat handler contains no try/catch and no .catch()

**Consequences to keep in mind while fixing.**
- Failures are indistinguishable in the logs, so the first step of every investigation is reproducing the request.
- A write that fails halfway leaves the record in an intermediate state that no later code expects.
- Error-rate metrics cannot separate client mistakes from dependency failures.

**Recommended remediation.** Wrap the I/O in try/catch (or a shared handler wrapper, which keeps every route consistent). In the catch: log with enough context to identify the operation and the record, map known failures onto honest status codes (400 for bad input, 404 for missing, 409 for a conflict, 503 for an unavailable dependency), and return a body the interface can act on. Keep internal details out of the response while putting them in the log. Where a handler performs several writes, run them in one transaction so a failure cannot leave the record half-updated.

**Estimated effort.** small
