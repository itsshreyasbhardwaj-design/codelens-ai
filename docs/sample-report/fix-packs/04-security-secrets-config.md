### 2. SEC-009 — User.password stores a credential in a column with no hashing indicated

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `prisma/schema.prisma`
- **References**: OWASP A02:2021 Cryptographic Failures; CWE-257 Storing Passwords in a Recoverable Format

**What is wrong.** The User model stores a credential in 'password'. The column name does not indicate a hash, and no password hashing library (bcrypt, argon2, scrypt, PBKDF2, or passlib) appears anywhere in the project, which indicates the value is stored as given.

**Why it matters to a user.** If this column holds raw credentials, a single read of the database — through a backup, a log, an injection flaw, or an insider — exposes every user's password, including on other services where those passwords are reused.

**Evidence.**
- `prisma/schema.prisma:7`
  ```
  // DEFECT (plaintext credential storage): no hash column, password stored raw.
  ```
  column holds a credential and no password hashing library was found anywhere in the project

**Recommended remediation.** Store only a verifier produced by a memory-hard password hash (argon2id preferred, otherwise scrypt or bcrypt) with a per-user salt. Rename the column to make that explicit (for example 'password_hash'), migrate by hashing on next successful login, and drop the old column once no rows depend on it.

**Estimated effort.** medium

### 4. SEC-014 — No HTTP security headers are configured

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `next.config.js`
- **References**: OWASP A05:2021 Security Misconfiguration; OWASP Secure Headers Project

**What is wrong.** No Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options, or Referrer-Policy header is set anywhere in the project. These headers are the browser-side defences that limit the damage of other flaws: CSP constrains what a successful script injection can do, HSTS prevents downgrade to plain HTTP, and nosniff stops a response being reinterpreted as script.

**Why it matters to a user.** Users are more exposed to consequences of other defects: an injected script faces fewer restrictions, a first visit can be intercepted over HTTP, and the full URL — including any identifiers in it — leaks to third-party sites through the referrer.

**Likely root cause.** Header configuration is not on by default in most frameworks and is easy to leave until later.

**Evidence.**
- `next.config.js:1`
  ```
  /** @type {import('next').NextConfig} */
  ```
  no headers() entry in the Next.js config and no header middleware found anywhere in the project

**Consequences to keep in mind while fixing.**
- A strict CSP usually needs iteration against the real page to avoid breaking legitimate scripts.
- HSTS is hard to roll back once a long max-age is cached by browsers: start with a short one.

**Recommended remediation.** Add a `headers()` entry to next.config.js returning Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, and a restrictive Permissions-Policy. Develop the CSP in report-only mode first, then enforce it, and begin HSTS with a short max-age before raising it.

**Estimated effort.** small
