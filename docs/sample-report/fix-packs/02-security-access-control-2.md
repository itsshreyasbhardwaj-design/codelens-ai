### 1. SEC-006 — POST /api/webhooks/stripe processes webhook payloads without verifying the signature

- **Severity**: critical
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/webhooks/stripe/route.ts`
- **References**: OWASP A08:2021 Software and Data Integrity Failures; CWE-345 Insufficient Verification of Data Authenticity

**What is wrong.** The handler acts on the request body without verifying that it came from the provider. The signature header is read, which suggests verification was intended, but the value is never checked against the signing secret. A webhook URL is effectively public: it must be assumed that attackers know it.

**Why it matters to a user.** Anyone can forge a request to this endpoint and cause whatever the handler does — marking orders paid, granting entitlements, or changing account state — without any real payment or provider event.

**Likely root cause.** Verification is commonly skipped during local development and then not added before release.

**Evidence.**
- `src/app/api/webhooks/stripe/route.ts:13`
  ```
  export async function POST(req: Request) {
  ```
  the signature header is read but never passed to a verification function

**Consequences to keep in mind while fixing.**
- Financial state can be changed by an unauthenticated caller.
- Provider-side event logs will not show the forged events, making reconciliation misleading.

**Recommended remediation.** Verify every delivery before acting on it: read the raw request body (not the parsed JSON, since re-serialising changes the bytes), compute or verify the HMAC against the provider signing secret with a constant-time compare — or use the provider SDK's own verification helper, such as Stripe's `constructEvent` — reject with 400 on failure, and enforce the provider's timestamp tolerance to prevent replay.

**Estimated effort.** small

### 2. SEC-015 — Session token is signed without an expiry

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/lib/auth.ts`
- **References**: OWASP A07:2021 Identification and Authentication Failures; CWE-613 Insufficient Session Expiration

**What is wrong.** The token is signed without an expiry claim, so it stays valid indefinitely. There is also no way to narrow the window of a leaked token short of rotating the signing key, which invalidates every session at once.

**Why it matters to a user.** A token captured from a shared machine, a log, or a proxy keeps working forever, so a user cannot really be logged out and a stolen session cannot be aged out.

**Evidence.**
- `src/lib/auth.ts:11`
  ```
  return jwt.sign(session, JWT_SECRET);
  ```
  token signed with no expiresIn or exp claim

**Recommended remediation.** Set a short expiry on access tokens (minutes to hours) and issue a separate, revocable refresh token. Keep a server-side record that lets an individual session be revoked without rotating the signing key for everyone.

**Estimated effort.** medium

### 3. SEC-016 — POST /api/chat performs no authentication check

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: security
- **Files**: `src/app/api/chat/route.ts`
- **References**: OWASP A01:2021 Broken Access Control; CWE-306 Missing Authentication for Critical Function

**What is wrong.** The handler for POST /api/chat does not call any session or authentication helper, and no rejection path for an unauthenticated caller exists in its body.

**Why it matters to a user.** An unauthenticated caller can change or destroy stored data.

**Likely root cause.** The route was added without the project's authentication helper, or enforcement was assumed to be global.

**Evidence.**
- `src/app/api/chat/route.ts:14`
  ```
  export async function POST(req: Request) {
  ```
  handler POST contains no authentication check

**Traced relationship** (route_authorization):
1. `src/app/api/chat/route.ts:14` (`POST`) — POST /api/chat handler declared
2. `src/app/api/chat/route.ts:14` (`POST`) — no call to a session or authentication helper in the handler body

**Consequences to keep in mind while fixing.**
- Client-side route guards do not mitigate this: the endpoint is reachable directly.
- Rate limiting and logging will record the access as anonymous traffic.

**Recommended remediation.** Resolve the session at the top of the handler using the project's existing helper, return 401 when it is absent, and then apply the authorisation rule for the resource. Enforce this server-side in the handler (or in middleware that provably matches this path), not in the client.

**Estimated effort.** small
