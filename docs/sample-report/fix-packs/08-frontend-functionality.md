### 3. A11Y-001 — Data is rendered with no loading or error state in src/app/products/page.tsx

- **Severity**: low
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: accessibility
- **Files**: `src/app/products/page.tsx`, `src/lib/db.ts`
- **References**: WCAG 2.2 4.1.3 Status Messages (Level AA); WCAG 2.2 3.3.1 Error Identification (Level A)

**What is wrong.** src/app/products/page.tsx awaits data as part of rendering (listAllProducts at line 6) and renders neither a pending state nor a failure state. This is an App Router segment, where the framework would supply both if the files existed: a loading.tsx renders while the segment streams, and an error.tsx catches anything the segment throws. Neither is present in this segment or any ancestor, and there is no Suspense or error boundary in an ancestor layout, so a rejection becomes the framework's own error screen and a slow response shows nothing at all. Two outcomes a user would experience differently are presented identically, with no text for assistive technology to announce. How long the request actually takes was not measured, and the failure path was not executed; those need a running system. This was derived from source only — no browser rendered the page during the scan, so the rendered result was not observed.

**Why it matters to a user.** On a slow connection the user sees an empty region with no indication that anything is happening, so they wait, reload, or leave. When the request fails they see the same empty region, with nothing telling them to retry and no way to distinguish failure from genuinely having no data. A screen-reader user gets no announcement at all, because nothing is rendered to announce.

**Likely root cause.** The happy path was built first; the pending and failure paths were left for later because they are not visible in local development against fast, working data.

**Evidence.**
- `src/app/products/page.tsx:6` (in `ProductsPage`)
  ```
  const products = await listAllProducts();
  ```
  data is awaited during render, and this module renders no pending or failure state
- `src/app/products/page.tsx:9`
  ```
  <div>
  ```
  the rendered output has no branch for a pending or failed request

**Traced relationship** (call):
1. `src/app/products/page.tsx:6` (`ProductsPage`) — awaits listAllProducts() while rendering, with no surrounding try/catch
2. `src/lib/db.ts` — listAllProducts is implemented here; a rejection or a slow response propagates to the caller unchanged
3. `src/app/products/page.tsx` — no error.tsx, global-error.tsx, loading.tsx, or Suspense/ErrorBoundary in an ancestor layout covers this route segment

**Consequences to keep in mind while fixing.**
- Support cannot distinguish "no data" from "the request failed" in user reports.
- A transient backend failure looks like data loss to the user.
- Perceived performance is worse than measured performance, because nothing acknowledges the wait.

**Recommended remediation.** Add a loading.tsx beside the page so the segment streams a skeleton while data resolves, and an error.tsx with a retry action so a rejection is contained in this segment. Mark the loading region with role="status" and aria-live="polite" so the wait is announced, and give the error state real text — what failed and what to do next — rather than only an icon. Keep an empty state distinct from both.

**Estimated effort.** small

### 4. A11Y-002 — Image without alt text in src/app/products/page.tsx

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: accessibility
- **Files**: `src/app/products/page.tsx`
- **References**: WCAG 2.2 1.1.1 Non-text Content (Level A); CWE-1100 Insufficient Isolation of System-Dependent Functions (accessibility); EN 301 549 clause 9.1.1.1

**What is wrong.** 1 image element(s) in src/app/products/page.tsx have no alt attribute at all (line 14). An absent alt is not the same as alt="": the empty string declares the image decorative and is skipped, whereas an absent attribute leaves assistive technology nothing to announce, so most screen readers fall back to reading the file name or URL. This was derived from source only — no browser rendered the page during the scan, so the rendered result was not observed. The attribute list is complete in the parsed markup, so the absence itself is not in doubt; what cannot be determined from source is whether the image carries information or is purely decorative.

**Why it matters to a user.** A screen-reader user reaches this image and hears a file path, or nothing. Where the image identifies a product, a status or an action, that information is simply missing for them, and any task that depends on it cannot be completed. The same gap affects anyone whose images fail to load.

**Likely root cause.** Markup written for the visual result only, with no linting rule (jsx-a11y/alt-text) failing the build when alt is absent.

**Evidence.**
- `src/app/products/page.tsx:14` (in `ProductsPage`)
  ```
  <img src={`/img/${p.id}.jpg`} width={200} height={200} />
  ```
  <img> with no alt attribute — no text alternative is present on this element

**Consequences to keep in mind while fixing.**
- Automated audits (axe, Lighthouse) will fail this page on a Level A criterion.
- Image-based navigation and search become unusable for assistive technology.

**Recommended remediation.** Add alt text describing the information the image conveys in its context — for a product image, the product name, not "image" or "photo". For an image that adds nothing beyond the adjacent text, set alt="" explicitly so it is skipped deliberately rather than by accident. When the image is the only content of a link or button, the alt text must describe the destination or action, not the picture. Add eslint-plugin-jsx-a11y with alt-text enabled so the next occurrence fails review instead of shipping.

**Estimated effort.** small

### 5. A11Y-003 — Control with no accessible name in src/app/products/page.tsx

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: accessibility
- **Files**: `src/app/products/page.tsx`
- **References**: WCAG 2.2 4.1.2 Name, Role, Value (Level A); WCAG 2.2 1.1.1 Non-text Content (Level A); WAI-ARIA Authoring Practices 1.2, keyboard interaction patterns

**What is wrong.** 1 interactive element(s) in src/app/products/page.tsx expose no accessible name (line 21). The accessible name is computed from the element's own labelling attributes and then from its content; here there is no aria-label, no aria-labelledby, no title, and the content contributes no text — an emoji, a symbol, an icon or nothing at all. The children are static in the source, so the computation can be followed to its end: the name is empty. A screen reader then announces only the role, for example "button", with nothing to distinguish it from any other button on the page. This was derived from source only — no browser rendered the page during the scan, so the rendered result was not observed.

**Why it matters to a user.** A screen-reader user hears "button" with no indication of what it does, and a voice-control user has no name to speak to activate it. Where the control is a primary action — add to basket, submit, delete — the task behind it is unreachable without sighted guessing.

**Likely root cause.** An icon or emoji was used as the whole label because it reads clearly to a sighted user, and the text alternative was never added.

**Evidence.**
- `src/app/products/page.tsx:21` (in `ProductsPage`)
  ```
  <button onClick={() => {}}>🛒</button>
  ```
  <button> whose only child is the non-text glyph "🛒", with no aria-label, aria-labelledby or title — no accessible name is available from children or attributes

**Consequences to keep in mind while fixing.**
- Voice control ("click add to basket") cannot target the element.
- Automated audits fail the page on WCAG 4.1.2, a Level A criterion.
- Tests that query by accessible name (Testing Library getByRole) cannot address the control either, so it tends to stay untested.

**Recommended remediation.** Give the control a name. Preferred: visible text alongside the icon, since it helps every user, not only assistive technology. Where the design requires icon-only, add aria-label="Add to basket" (the action, not the icon), or render visually hidden text inside the control with a .sr-only utility. Mark the icon itself aria-hidden="true" so it is not announced twice. Enable eslint-plugin-jsx-a11y rules control-has-associated-label and anchor-has-content to catch the next one at review time.

**Estimated effort.** small
