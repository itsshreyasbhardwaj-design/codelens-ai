### 1. QUAL-001 — priceWithDiscount() and computeDiscount(): near-duplicate logic that has already drifted apart

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: quality
- **Files**: `src/server/legacy.ts`
- **References**: Martin Fowler, Refactoring (2nd ed.) — Duplicated Code, Long Function, Shotgun Surgery; CWE-1041 Use of Redundant Code

**What is wrong.** priceWithDiscount() and computeDiscount(), both in src/server/legacy.ts, implement the same rule twice. After stripping comments and normalising whitespace, their bodies are 98% identical as token sequences — close enough that one was copied from the other, and not identical. The bodies line up statement for statement except at one line: src/server/legacy.ts:19 reads `if (code === 'SAVE20') return Math.round(cents * 0.8);` while src/server/legacy.ts:25 reads `if (code === 'SAVE20') return Math.round(cents * 0.85);`. The difference is not cosmetic — a literal, an operator or a comparison differs — so the two copies compute different answers for the same input. Two copies that still agree are a tidiness problem. Two copies that have drifted are a correctness problem that is invisible at every individual call site: whichever copy a caller happens to reach decides the answer it gets, and both call sites look correct on their own.

**Why it matters to a user.** Users get different results from the same input depending on which code path serves their request — one route, job or screen applies the older version of the rule and another applies the newer one, with no error raised in either. When the rule is next corrected in one copy, the other keeps the old behaviour, so the defect reappears for whoever takes the untouched path, and it reappears without any change to the code that gets blamed.

**Likely root cause.** One function was copied to serve a second caller — typically because the original was awkward to import from — and a later change was applied to only one of them.

**Evidence.**
- `src/server/legacy.ts:19`
  ```
  if (code === 'SAVE20') return Math.round(cents * 0.8);
  ```
  priceWithDiscount() — first copy of the logic
- `src/server/legacy.ts:25`
  ```
  if (code === 'SAVE20') return Math.round(cents * 0.85);
  ```
  computeDiscount() — second copy, which disagrees with the first at this line

**Consequences to keep in mind while fixing.**
- A fix or a test added against one copy gives no protection to the other.
- Reviewers reading either copy in isolation see nothing wrong, so the divergence survives review.
- Any further copy made from either version inherits that version of the rule.

**Recommended remediation.** Decide which behaviour is correct — the two cannot both be — then keep exactly one implementation and have the other call site use it. Keep the surviving function in this file and delete the other. Before deleting, write a test for each input where the two disagreed, pinning the intended answer, so the behaviour change on the losing call path is deliberate and visible in the diff instead of a side effect of the refactor.

### 6. QUAL-007 — src/lib/db.ts exports prisma, pool as an import-time singleton, which leaves tests no seam

- **Severity**: low
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: quality
- **Files**: `src/lib/db.ts`
- **References**: Michael Feathers, Working Effectively with Legacy Code — seams; The Twelve-Factor App — III. Config

**What is wrong.** This is the shared-instance pattern several frameworks recommend for a dedicated client module, so it is reported as an observation rather than a defect. src/lib/db.ts creates prisma, pool as a module-scope value, and 6 module(s) import this file. Because the construction happens on import rather than on first use, every one of those modules — and anything that imports them — runs it merely by being loaded. There is no exported factory and nothing is passed in, so there is no point at which a caller or a test can supply a different implementation. The consequence is that a unit test for any of the importers is not a unit test: it needs the real client to be constructible in the test process, which usually means it needs the real service. The construction also reads configuration (DATABASE_URL) at import time, so a missing or wrong value fails at module load, before any code can report a useful error.

**Why it matters to a user.** Users feel this as untested code paths reaching production: the handlers that depend on this module are the expensive ones to test, so in practice they are tested least, and regressions in them are found by users rather than by CI. It also changes how failures present: a configuration problem takes the process down at start-up instead of producing a clear error on the one feature that needs the service.

**Likely root cause.** A shared singleton was the quickest way to avoid reconnecting per request, and the trade-off against substitutability was never revisited.

**Evidence.**
- `src/lib/db.ts:4`
  ```
  export const prisma = new PrismaClient();
  ```
  prisma is constructed at module scope, so importing this file performs the construction
- `src/lib/db.ts:5`
  ```
  export const pool = new Pool({ connectionString: process.env.DATABASE_URL });
  ```
  pool is constructed at module scope, so importing this file performs the construction

**Traced relationship** (import):
1. `src/lib/db.ts:4` — prisma, pool constructed at module scope
2. `src/app/api/admin/stats/route.ts` — imports this module, so it inherits that construction
3. `src/app/api/login/route.ts` — imports this module, so it inherits that construction
4. `src/app/api/orders/[id]/route.ts` — imports this module, so it inherits that construction
5. `src/app/api/webhooks/stripe/route.ts` — imports this module, so it inherits that construction
6. `src/app/products/page.tsx` — imports this module, so it inherits that construction
7. `src/lib/db.ts` — no exported factory or injection point returns the client, so a caller cannot substitute one

**Consequences to keep in mind while fixing.**
- Tests of the importing modules are integration tests whether or not they are labelled as such.
- Teams reach for module mocking to work around this, which couples tests to import paths and breaks on refactor.
- Connections are opened by any process that imports the module, including scripts and build steps that never query.

**Recommended remediation.** Introduce a seam without giving up the singleton: export a function that returns the client and creates it on first call, and let callers accept the client (or that function) as a parameter with the shared instance as the default. Keep configuration reading inside that function so a missing value is reported when the feature is used, with the variable name in the message. Tests then pass a fake in directly, and no module-mocking framework is needed.

### 8. QUAL-003 — TypeScript strict mode is switched off in tsconfig.json

- **Severity**: medium
- **Confidence**: CONFIRMED — the evidence is conclusive
- **Category**: quality
- **Files**: `tsconfig.json`
- **References**: TypeScript handbook — Compiler Options: strict; CWE-704 Incorrect Type Conversion or Cast

**What is wrong.** tsconfig.json sets "strict": false. 13 TypeScript source file(s) are compiled under it. With strict off, the two checks that catch the most real defects are both inactive: `strictNullChecks`, so every type silently includes `null` and `undefined` and the compiler accepts reading a property off a value that may not be there; and `noImplicitAny`, so a parameter or variable the compiler cannot infer becomes `any` and stops being checked at all, along with everything derived from it. The project therefore pays the cost of type annotations without getting the guarantee they imply — reviewers reading a signature reasonably assume the compiler is enforcing it, and here it is not. A compiler flag passed on the command line could override this; check the build invocation before concluding how the production build is actually compiled.

**Why it matters to a user.** The failures this allows through are the ones users meet as a blank screen or a 500: a value that was absent at runtime is read as if it were present, and the error surfaces far from the code that let it through. Because the type system is not enforcing the contract, these defects are found by users rather than by the build.

**Likely root cause.** Strict mode was left off (or switched off) to get an existing codebase compiling, and enabling it later became a bigger task than any one change could absorb.

**Evidence.**
- `tsconfig.json:1`
  ```
  { "compilerOptions": { "strict": false, "target": "ES2022", "jsx": "preserve", "module": "esnext", "moduleResolution": "bundler" } }
  ```
  strict checking is switched off here

**Consequences to keep in mind while fixing.**
- Every file added while strict is off accumulates more code that will not compile when it is turned on.
- Editor tooling and type-aware lint rules are weaker across the whole project, not just in the unsound files.
- `any` introduced at a boundary spreads through inference into code that looks fully typed.

**Recommended remediation.** Turn strict on at the project level and work the errors down rather than suppressing them. The migration that works in a live codebase: enable `strict` in the base configuration, then add the narrowest possible per-directory override (or a short include/exclude list) for the areas that cannot be fixed immediately, so new code is checked from today. Fix `strictNullChecks` errors by handling the absent case explicitly at the boundary where the value enters, not by adding `!`. Treat each remaining override as a tracked item with an owner, since an override with no end date is the same as leaving the flag off.

**Estimated effort.** large
