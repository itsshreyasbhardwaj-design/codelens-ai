### 1. OPS-001 — .env is baked into the container image by `COPY . .`

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `Dockerfile`, `.env`
- **References**: Docker — Build context and .dockerignore; CWE-538 Insertion of Sensitive Information into Externally-Accessible File or Directory; Twelve-Factor App — III. Config; OWASP A05:2021 Security Misconfiguration

**What is wrong.** Dockerfile copies the entire build context with `COPY . .`, and .env is tracked in the repository, so the file becomes part of the image. No .dockerignore exists, so nothing is excluded from the build context. An image layer is not private storage: anyone who can pull the image can extract the file with `docker save`, and the layer persists in the registry and in the build cache even if a later instruction deletes the file. This is distinct from the file being committed at all — that is a source-control problem; this is the image distributing it to every host, CI job, and registry mirror that ever receives a pull.

**Why it matters to a user.** Users are exposed indirectly: every credential in that file — database, payment provider, token-signing key — is readable by anyone who obtains the image, and those credentials are usually enough to read customer records or spend money on the account. Because the leak path is the image rather than the source tree, it keeps working after the file is removed from the repository.

**Likely root cause.** `COPY . .` is the shortest way to get an application into an image, and the build context quietly includes dotfiles.

**Evidence.**
- `Dockerfile:4`
  ```
  COPY . .
  ```
  copies the entire build context, including .env, into the runtime image
- `.env:9`
  ```
  DATABASE_URL=<value deliberately not reproduced>
  ```
  this file is tracked in the repository and is not excluded by a .dockerignore entry

**Traced relationship** (env_var):
1. `.env:9` — environment file tracked in the repository
2. `Dockerfile:4` — COPY . . copies the whole build context
3. `Dockerfile:1` — the copy happens in the stage that produces the runtime image

**Consequences to keep in mind while fixing.**
- Deleting the file in a later RUN does not remove it: the earlier layer still contains it.
- Every credential in the file must be rotated, not just excluded from future builds.
- Registry mirrors, CI caches, and local pulls hold copies that are outside the repository's control.

**Recommended remediation.** Add a .dockerignore that excludes `.env*`, `.git`, `node_modules`, and local tooling output, then copy only what the image needs (the manifest and lockfile, then the build output) rather than the whole context. Supply configuration at run time through the orchestrator's environment or secret mechanism, and use build secrets (`RUN --mount=type=secret`) when a value is genuinely needed during the build, since those are not written to a layer. Treat every value in the file as compromised and rotate it.

### 2. OPS-003 — The service is containerised but exposes no health or readiness endpoint

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `Dockerfile`, `src/app/api/admin/stats/route.ts`
- **References**: Kubernetes — Configure liveness, readiness and startup probes; Google SRE Workbook — Alerting on SLOs

**What is wrong.** Dockerfile describes how this service is run, and the project exposes 9 detected route(s), none of which is a health, readiness, or liveness endpoint. Nothing therefore distinguishes "the process is running" from "the process can serve a request": not the container runtime, not a load balancer, not a deployment that needs to know whether the new version came up. The routes considered here are the ones this scanner resolved statically, so an endpoint served by a framework mechanism it does not model would not appear — but no probe configuration pointing at such an endpoint exists either, which is the corroborating half of this observation.

**Why it matters to a user.** During a partial failure — a lost database connection, an exhausted pool, a blocked event loop — the instance stays in rotation and users keep being sent to it, receiving timeouts rather than being routed to a working instance. During a deployment, a new version that starts but cannot serve traffic is treated as a success, so users can be moved onto a broken release.

**Likely root cause.** Health endpoints are infrastructure rather than product work, so they are added after the first incident that needed one.

**Evidence.**
- `Dockerfile:1`
  ```
  FROM node:20
  ```
  this configuration defines how the service is run, and no readiness or liveness target exists for it
- `src/app/api/admin/stats/route.ts:11`
  ```
  export async function GET() {
  ```
  one of 9 detected routes; none of them is a health or readiness endpoint

**Traced relationship** (import):
1. `Dockerfile:1` — the service is packaged to run under a container runtime or platform
2. `src/app/api/admin/stats/route.ts:11` — 9 routes detected across the project
3. `Dockerfile` — none of the detected routes answers a health, readiness, or liveness check, and no probe is configured

**Consequences to keep in mind while fixing.**
- Zero-downtime and rolling deployments cannot be relied on without a readiness signal.
- Autoscaling and restart decisions have nothing to act on but process exit.
- Uptime monitoring can only probe a real user-facing route, which mixes application errors with availability.

**Recommended remediation.** Add two cheap, unauthenticated endpoints and wire them up: a liveness route that returns 200 if the process is responsive, and a readiness route that checks the dependencies a request needs (database connectivity, cache, required configuration) and returns a non-2xx status when any is unusable. Reference them from the container HEALTHCHECK and from the orchestrator's liveness and readiness probes, keep them out of request logging and rate limiting, and make sure readiness failure drains traffic rather than restarting the process.

**Estimated effort.** small

### 3. OPS-004 — Dockerfile defines no USER, so the container runs as root

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `Dockerfile`
- **References**: CIS Docker Benchmark — 4.1 Create a user for the container; CWE-250 Execution with Unnecessary Privileges; Docker — Best practices for writing Dockerfiles

**What is wrong.** The runtime stage of Dockerfile contains no USER directive. Official base images do not drop privileges for you, so the application process runs as uid 0 inside the container. A root process inside a container can write anywhere in the image filesystem, install packages at runtime, and bind privileged ports; where the container runtime is not additionally hardened (user namespaces, a seccomp or AppArmor profile, a read-only root filesystem, dropped capabilities) root in the container is a much shorter distance from root on the host than most teams assume. It also makes any code-execution defect elsewhere in the application considerably more useful to an attacker.

**Why it matters to a user.** Users are not affected while the application behaves normally. If an attacker achieves code execution through another defect, running as root is what turns a limited foothold into full control of the container: application files and secrets can be rewritten, a persistent backdoor can be installed, and outbound traffic can be redirected, which users experience as tampered pages, leaked data, or a service that has to be rebuilt from scratch.

**Likely root cause.** The Dockerfile was written from a base-image quickstart, which never includes a USER line.

**Evidence.**
- `Dockerfile:1`
  ```
  FROM node:20
  ```
  no USER directive applies to this stage, so the process keeps the base image default of uid 0 (comments are stripped before matching, so a comment about USER does not count)
- `Dockerfile:13`
  ```
  CMD ["npm", "start"]
  ```
  this is the process that runs as root

**Consequences to keep in mind while fixing.**
- Kubernetes `runAsNonRoot` or a restricted Pod Security Standard will refuse to schedule this image once such a policy is adopted.
- Files the container writes to a mounted volume will be owned by root on the host, which is awkward to undo later.

**Recommended remediation.** Create an unprivileged account in the image and switch to it before the process starts: add a group and user (for example `RUN addgroup --system --gid 1001 app && adduser --system --uid 1001 app`, or use the `node` user that Node images already ship), chown only the paths the process must write, then add `USER app` as the last instruction before CMD/ENTRYPOINT. Keep writable state on a mounted volume or a tmpfs rather than widening permissions in the image, and pair this with a read-only root filesystem and dropped capabilities in the orchestrator manifest.

**Estimated effort.** small

### 4. OPS-006 — Dockerfile builds on a floating base image tag (node:20)

- **Severity**: low
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `Dockerfile`
- **References**: OpenSSF Scorecard — Pinned-Dependencies check; SLSA v1.0 — Build track, hermetic and reproducible builds; CWE-1104 Use of Unmaintained Third Party Components

**What is wrong.** The base image is referenced as `node:20`, which resolves to whatever the publisher currently points that tag at. Two builds of the same commit can therefore produce different images: a different runtime patch level, different system libraries, and a different set of CVEs. That is the opposite of what a build should be — the image is part of the artefact, so it needs to be as fixed as the application code. It also means a compromised or mistakenly republished upstream tag enters the build with no review and no record of the change.

**Why it matters to a user.** Users see failures that do not correspond to any change in the application: a deploy that worked yesterday breaks today because the base image moved underneath it, and the failure cannot be reproduced from the repository at that commit.

**Likely root cause.** The tag was copied from the image's quickstart documentation, which always shows the convenient moving tag.

**Evidence.**
- `Dockerfile:1`
  ```
  FROM node:20
  ```
  base image tag '20' moves whenever the publisher re-tags it, and no digest pins it

**Consequences to keep in mind while fixing.**
- A rebuild is not a safe recovery action: it may pull a different base than the image currently in production.
- Vulnerability scan results cannot be tied to a specific commit, because the scanned image is not reproducible from it.

**Recommended remediation.** Pin the base image by digest (`FROM node:20@sha256:<digest>`), keeping the human-readable tag for context, and let an automated update tool raise the digest in a reviewable pull request. Record the resolved digest in the build log or image labels so the running image can always be traced back to a commit.

**Estimated effort.** trivial

### 5. OPS-009 — Dockerfile declares no health check for the container

- **Severity**: low
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `Dockerfile`
- **References**: Kubernetes — Configure liveness, readiness and startup probes; Docker — Best practices for writing Dockerfiles

**What is wrong.** Dockerfile has no HEALTHCHECK, and no liveness or readiness probe appears in any committed compose, Kubernetes, or platform configuration. Without one, the only liveness signal available to whatever runs this image is whether process 1 is still alive. The failure modes that matter in production are precisely the ones that keep the process alive: an exhausted connection pool, an event loop blocked on a synchronous call, a deadlock, or a dependency that stopped answering. In each case the container looks healthy, stays in the load-balancer rotation, and keeps receiving traffic.

**Why it matters to a user.** When the application wedges rather than crashes, users keep being routed to the broken instance: requests hang or time out, and nothing restarts or drains it until a human notices. Rolling deployments are affected too — a new version that starts but cannot serve traffic is treated as a success and the old, working version is removed.

**Likely root cause.** A health check needs an endpoint to call, so it is commonly deferred until the first production incident.

**Evidence.**
- `Dockerfile:13`
  ```
  CMD ["npm", "start"]
  ```
  no HEALTHCHECK directive exists in this file and no orchestrator probe was found in any committed deployment configuration

**Consequences to keep in mind while fixing.**
- Zero-downtime deployment cannot be relied on: nothing distinguishes "process started" from "ready to serve".
- Autoscaling and restart policies have no signal to act on other than process exit.

**Recommended remediation.** Add an endpoint that checks the dependencies a request actually needs (database connectivity, cache, required configuration) and returns a non-2xx status when any of them is unusable, then wire it up: `HEALTHCHECK --interval=30s --timeout=3s --start-period=30s --retries=3 CMD <http client> -f http://localhost:<port>/healthz || exit 1` in the image, and the equivalent liveness and readiness probes in the orchestrator manifest, where readiness gates traffic and liveness triggers a restart. Keep the check cheap and unauthenticated, and do not make it depend on a service whose outage should not take this one down.

**Estimated effort.** small

### 6. OPS-012 — Dockerfile ships its build toolchain in the runtime image

- **Severity**: low
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: devops
- **Files**: `Dockerfile`
- **References**: Docker — Multi-stage builds; Docker — Best practices for writing Dockerfiles

**What is wrong.** Dockerfile declares a single stage, and that stage installs dependencies without restricting them to production (and in some cases compiles the project) in the same image that is run. Everything needed to build therefore ships to production: compilers, development dependencies, source maps, and the package manager itself. Each of those is extra attack surface that the application never uses at run time, and each contributes to a larger image, which means slower pulls, slower rollbacks, and more to scan and patch.

**Why it matters to a user.** No direct user-visible effect in normal operation. Users feel it during an incident: a larger image takes longer to pull, which lengthens both a deploy and the rollback that ends an outage.

**Likely root cause.** A single-stage Dockerfile is the simplest thing that works, and splitting it is rarely urgent.

**Evidence.**
- `Dockerfile:5`
  ```
  RUN npm install
  ```
  build-time dependencies are installed into the same stage that produces the runtime image; this file declares only one FROM

**Consequences to keep in mind while fixing.**
- Vulnerability scanners report findings in build-only packages, which dilutes the signal from ones that matter.
- Development dependencies in the runtime image give a code-execution foothold more tools to work with.

**Recommended remediation.** Split the Dockerfile into a build stage and a runtime stage: install all dependencies and build in the first stage, then start the runtime stage from a slim or distroless base and `COPY --from=build` only the build output plus the production dependency tree (installed with `npm ci --omit=dev` or the equivalent). Keep the lockfile copy before the source copy so dependency layers stay cached, and set a non-root USER in the runtime stage.

**Estimated effort.** small
