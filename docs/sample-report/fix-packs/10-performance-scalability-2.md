### 1. COST-005 — WebhookEvent accumulates rows with traffic and nothing in the project removes them

- **Severity**: low
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: cost
- **Files**: `prisma/schema.prisma`, `src/app/api/webhooks/stripe/route.ts`
- **References**: CWE-400 Uncontrolled Resource Consumption; AWS Well-Architected Framework — Cost Optimization Pillar (match supply to demand; measure before optimising); docs/LIMITATIONS.md — this scan has no billing or usage data, so no cost figure is produced

**What is wrong.** WebhookEvent gains a row every time the code path above runs, and no code path in this project ever removes one. No read of this table appears anywhere either, so the rows are written, stored, and backed up without being used. Storage and backup are billed by volume, and backups multiply whatever the table holds, so this grows monotonically for as long as the application runs. Retention could be enforced outside this repository — a database-side job, a provider policy, a partition schedule — which this scan cannot see; that is why this is reported as a gap to confirm rather than as a fact.

**Why it matters to a user.** Nothing is visible to users at first. The effects arrive indirectly and together: backups and restores take longer, queries that touch the table slow down as it grows, and the storage line on the bill rises without any change in traffic.

**Likely root cause.** The table was added to record something useful, and no one owned the question of how long the records should live.

**Evidence.**
- `src/app/api/webhooks/stripe/route.ts:22`
  ```
  await prisma.webhookEvent.create({ data: { eventId: event.id, type: event.type } });
  ```
  rows are appended here; no call anywhere in the project deletes, expires, or archives this table
- `prisma/schema.prisma:43`
  ```
  model WebhookEvent {
  ```
  WebhookEvent records events over time and declares no expiry or retention field

**Traced relationship** (data_policy):
1. `prisma/schema.prisma` — WebhookEvent is an append-only record of events, keyed by time
2. `src/app/api/webhooks/stripe/route.ts:22` (`POST`) — prisma.webhookEvent.create() inserts a row per occurrence
3. `prisma/schema.prisma` — no delete, truncate, expiry, TTL, or archival path for this table exists in the code or configuration read by this scan

**Consequences to keep in mind while fixing.**
- Restore time grows with the table, so recovery gets slower as a side effect of an unrelated feature.
- Personal data kept indefinitely becomes a compliance question as well as a cost one.
- Index maintenance and autovacuum work grow with the table, taxing queries that do not touch it.

**Recommended remediation.** Decide a retention period for this table and enforce it in code you can see: a scheduled job that deletes or archives rows past the cut-off, with a bounded batch size so the delete itself cannot overload the database. Where the data has analytic value beyond the retention period, roll it up into aggregates and keep those rather than the raw rows, or move the raw rows to cheaper object storage. Add the retention period to the model documentation so the next table of this kind starts with one.

### 2. COST-006 — Prisma and node-postgres are two independent database access paths

- **Severity**: low
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: cost
- **Files**: `package.json`, `src/lib/db.ts`, `src/app/api/admin/stats/route.ts`
- **References**: AWS Well-Architected Framework — Cost Optimization Pillar (match supply to demand; measure before optimising); CWE-400 Uncontrolled Resource Consumption

**What is wrong.** The project queries its database two ways: through Prisma and directly through node-postgres. Each client maintains its own connection pool, so a process that loads both holds two sets of connections — and connections are a bounded, billed resource on every managed database, charged for whether or not they are carrying queries. The second pool is also constructed when its module is imported, so a process pays for it even on request paths that only use the other one. A raw driver alongside an ORM is legitimate where a query cannot be expressed in Prisma; this is reported so the choice is a decision rather than an accident.

**Why it matters to a user.** The symptom appears under load rather than in normal use: the two pools together exhaust the database connection limit, and requests then fail to acquire a connection — including requests to features that had nothing to do with the heavy path.

**Likely root cause.** A query the ORM could not express, or an older access layer that was never retired after the ORM was introduced.

**Evidence.**
- `src/lib/db.ts:13`
  ```
  const result = await pool.query(sql);
  ```
  node-postgres is used to query directly, with its own connection pool
- `src/app/api/admin/stats/route.ts:12`
  ```
  const users = await prisma.user.findMany({ include: { orders: true } });
  ```
  Prisma queries the same database through its own client
- `package.json:19`
  ```
  "pg": "8.13.0",
  ```
  node-postgres declared alongside Prisma
- `package.json:24`
  ```
  "prisma": "5.20.0",
  ```
  Prisma declared alongside node-postgres

**Traced relationship** (import):
1. `package.json` — Prisma ('prisma') and node-postgres ('pg') are both declared
2. `src/app/api/admin/stats/route.ts:12` — 7 queries go through Prisma
3. `src/lib/db.ts:13` — 1 query goes through node-postgres directly
4. `src/lib/db.ts` — each client maintains its own connection pool, so the two are additive against the database connection limit

**Consequences to keep in mind while fixing.**
- Connection limits must be reasoned about across two pools, so the safe ceiling per instance is easy to get wrong.
- Raw-driver queries bypass the ORM's generated types and its query logging, so they are invisible to the tooling used to review the rest of the data layer.
- Two access layers mean two places to apply a schema change.

**Recommended remediation.** Decide which access path owns normal queries — in most projects that is Prisma — and express the remaining raw queries through its own escape hatch for parameterised SQL, so one pool serves the process. If the raw driver must stay, construct it lazily rather than at module load, give both pools explicit bounds whose sum fits inside the database connection limit with headroom for migrations and admin sessions, and keep its use confined to one module.

**Estimated effort.** medium

### 3. PERF-007 — Raw <img> used in a Next.js view instead of the framework's image component

- **Severity**: low
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: performance
- **Files**: `src/app/products/page.tsx`
- **References**: web.dev: Optimize images; docs/LIMITATIONS.md — this scan does not measure runtime behaviour

**What is wrong.** This module renders 1 plain <img> element and does not import next/image, so the framework's image pipeline is bypassed: no resizing per viewport, no modern-format negotiation (AVIF/WebP), and no automatic lazy-loading or caching policy. The browser downloads whatever file the src points at, at whatever dimensions it was authored, however small the rendered box is. Explicit width and height are set, which does avoid layout shift. The actual file sizes are not read by this scan, so the size of the waste is unknown.

**Why it matters to a user.** Users download more image data than their screen can use, which is slowest and most expensive exactly where it matters most — mobile connections and metered data. The page also takes longer to become stable and interactive while the images arrive.

**Likely root cause.** The markup was written as plain HTML, which works, so the framework component was never swapped in.

**Evidence.**
- `src/app/products/page.tsx:14`
  ```
  <img src={`/img/${p.id}.jpg`} width={200} height={200} />
  ```
  plain <img> element with no srcSet/sizes, so one file is served to every viewport

**Consequences to keep in mind while fixing.**
- Image weight tends to grow silently as content is added, because nothing in the pipeline enforces a ceiling.
- Off-screen images compete with above-the-fold content for bandwidth.

**Recommended remediation.** Use next/image (or the framework's equivalent) with explicit width and height, or `fill` with a sized container, so the pipeline generates and caches per-viewport variants in modern formats. Configure the allowed remote patterns narrowly rather than permitting every host. Where a plain <img> must stay — an inline SVG, or an external host that cannot be proxied — declare srcSet and sizes, set width and height, and add loading="lazy" plus decoding="async" for anything below the fold.

**Estimated effort.** small
