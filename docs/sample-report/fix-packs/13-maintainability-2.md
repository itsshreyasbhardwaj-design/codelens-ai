### 1. QUAL-004 — 5 environment variables are read ad hoc across 4 modules

- **Severity**: low
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: quality
- **Files**: `src/app/api/admin/stats/route.ts`, `src/app/api/chat/route.ts`, `src/lib/auth.ts`, `src/lib/db.ts`
- **References**: The Twelve-Factor App — III. Config; CWE-1188 Insecure Default Initialization of Resource

**What is wrong.** 5 environment variables are read at 4 separate points in the source, and no module collects and validates them. Two specific things follow. First, nothing checks that a required value is present or well formed, so a missing or malformed variable is not detected at start-up — it is detected when some code path finally reads it and gets `undefined`, which is a request-time failure in whichever feature touched it first. Second, each read site decides for itself what the value means: 3 of these reads supply their own inline default, so the same variable can behave differently in two places, and a reader cannot tell what the application requires without finding every read. 2 of the variables are not listed in any example or template file, so the required set is not written down anywhere either.

**Why it matters to a user.** A deployment with a missing or wrong configuration value starts successfully and then fails for users on the specific feature that needs it — often intermittently, and often long after the deployment that caused it, which makes it hard to connect the two. Where a read supplies its own default, the failure is worse than an error: the feature works, quietly, with the wrong value.

**Likely root cause.** Each variable was read where it was needed, which is the path of least resistance, and no module ever took ownership of configuration as a whole.

**Evidence.**
- `src/app/api/admin/stats/route.ts:9`
  ```
  const adminEmails = (process.env.ADMIN_EMAILS ?? '').split(',');
  ```
  ADMIN_EMAILS is read here, directly from the environment, with an inline fallback
- `src/app/api/chat/route.ts:4`
  ```
  const client = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });
  ```
  OPENAI_API_KEY is read here, directly from the environment
- `src/lib/auth.ts:5`
  ```
  const JWT_SECRET = process.env.JWT_SECRET || 'dev-secret-key-change-me-in-prod-12345';
  ```
  JWT_SECRET is read here, directly from the environment, with an inline fallback
- `src/lib/auth.ts:29`
  ```
  export const sessionTtlHours = Number(process.env.SESSION_TTL_HOURS ?? 24);
  ```
  SESSION_TTL_HOURS is read here, directly from the environment, with an inline fallback

**Traced relationship** (env_var):
1. `src/app/api/admin/stats/route.ts:9` — ADMIN_EMAILS read directly from the environment
2. `src/app/api/chat/route.ts:4` — OPENAI_API_KEY read directly from the environment
3. `src/lib/auth.ts:5` — JWT_SECRET read directly from the environment
4. `src/lib/auth.ts:29` — SESSION_TTL_HOURS read directly from the environment
5. `src/lib/db.ts:5` — DATABASE_URL read directly from the environment
6. `src/app/api/admin/stats/route.ts` — no module in the project reads and validates the configuration in one place

**Consequences to keep in mind while fixing.**
- The set of variables a deployment needs can only be discovered by searching the code, so it drifts from the documented set.
- Inline defaults mask absent configuration in production, which is the hardest class of configuration bug to find.
- Tests and local development diverge from deployment because nothing asserts the same required set in both.

**Recommended remediation.** Read configuration in one module, once, at start-up: parse every variable there, coerce it to the type the application wants, fail immediately with a message naming the variable when a required one is absent or invalid, and export the resulting typed object. Have the rest of the code import that object instead of touching the environment. Keep the example or template file generated from the same declaration so it cannot drift, and keep defaults in that one place where they can be reviewed — a default buried at a read site is indistinguishable from working configuration.

**Estimated effort.** medium
