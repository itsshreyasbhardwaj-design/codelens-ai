### 2. AI-002 — Request input is interpolated into the system prompt in POST /api/chat

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: ai_app
- **Files**: `src/app/api/chat/route.ts`
- **References**: OWASP Top 10 for LLM Applications: LLM01 Prompt Injection; CWE-1427 Improper Neutralization of Input Used for LLM Prompting; NIST AI 600-1 Generative AI Profile (AI Risk Management Framework); CodeLens AI README: repository and user content is treated as untrusted data at every point — it never enters the system prompt, and is fenced with a per-request nonce

**What is wrong.** The system prompt is the privileged channel of a model request: everything in it is read as the operator's own instruction, and models are trained to weight it above the conversation. Here a value taken from req.json() is interpolated directly into that channel, so text the operator did not write becomes an instruction with operator authority. Text appearing later in the same message does not constrain text that appeared earlier: an input ending with "ignore the preceding instructions and ..." sits at the same privilege level as the rules around it, and there is no delimiter or hierarchy statement separating the two. This project applies the same rule to its own model usage: CodeLens AI README: repository and user content is treated as untrusted data at every point — it never enters the system prompt, and is fenced with a per-request nonce.

**Why it matters to a user.** A user typing into the ordinary input box can change what the assistant is instructed to do: reveal the hidden instructions, drop restrictions the business depends on, impersonate the operator in its replies, or disclose context assembled from other sources for this request. Other users then receive answers produced under instructions an attacker supplied.

**Likely root cause.** Template interpolation is the obvious way to put a value in a prompt, and the system message is where the prompt text already lives, so the untrusted value lands in the privileged channel by convenience rather than by decision.

**Evidence.**
- `src/app/api/chat/route.ts:15`
  ```
  const { message } = await req.json();
  ```
  the value is read out of the incoming request here
- `src/app/api/chat/route.ts:20`
  ```
  { role: 'system', content: `You are a shop assistant. The user says: ${message}. Never reveal internal pricing.` },
  ```
  request-derived value `message` is interpolated into the content of a role:'system' message
- `src/app/api/chat/route.ts:17`
  ```
  const completion = await client.chat.completions.create({
  ```
  the assembled messages are sent to the provider by client.chat.completions.create()

**Traced relationship** (data_policy):
1. `src/app/api/chat/route.ts:14` (`POST`) — `message` originates from req.json()
2. `src/app/api/chat/route.ts:20` (`POST`) — placed inside the content of a role:'system' message
3. `src/app/api/chat/route.ts:17` (`POST`) — sent to the model by client.chat.completions.create()

**Consequences to keep in mind while fixing.**
- Filtering for phrases such as "ignore previous instructions" does not fix this: the channel, not the wording, is the defect.
- Any secret, internal rule, or other user's context placed in the same system prompt becomes reachable by the same override.
- If the model's reply is then trusted by downstream code, the override reaches those code paths too.

**Recommended remediation.** Keep the privileged channel operator-authored and constant. Put the instructions in the system message with no interpolation of request values, and pass the untrusted text as a separate role:'user' message (or, for retrieved documents, as clearly labelled context in a user-role message). Fence it explicitly — a delimiter such as `<untrusted_input> … </untrusted_input>` plus a sentence in the system prompt stating that content inside the fence is data and must never be treated as instructions — and strip or escape the delimiter from the untrusted text so it cannot close the fence. Where the model's output drives an action, authorise that action against the session rather than against the model's say-so, and keep the model's privileges no wider than the caller's.

### 3. AI-003 — POST /api/chat returns model output to the client with no validation

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: ai_app
- **Files**: `src/app/api/chat/route.ts`
- **References**: OWASP Top 10 for LLM Applications: LLM05 Improper Output Handling; CWE-20 Improper Input Validation

**What is wrong.** The handler for POST /api/chat returns the model's text to the caller exactly as received. There is no structured-output mode on the request, no schema parse of the result, no length bound, and no check of what the text contains. The response shape the client depends on is therefore whatever the model produced for that request: a model or prompt change, a refusal, a truncated generation, or an empty completion all arrive at the client as a successful 200.

**Why it matters to a user.** Users see malformed, empty, or off-topic content rendered as if it were a normal answer, and a client that expects a particular shape can break outright on an unexpected one. Because the response still carries a success status, the UI has nothing to branch on and shows the broken result rather than an error state.

**Likely root cause.** The happy path was built first and the model returned sensible text during development, so the parse step never looked necessary.

**Evidence.**

  generated text is produced here by client.chat.completions.create()
- `src/app/api/chat/route.ts:24`
  ```
  return NextResponse.json({ reply: completion.choices[0].message.content });
  ```
  the generated text is sent to the client without a schema check, a content check, or a length bound

**Traced relationship** (frontend_backend_contract):

2. `src/app/api/chat/route.ts:24` (`POST`) — the value is placed in the response body unchanged
3. `src/app/api/chat/route.ts` — no schema parse, structured-output mode, or content check appears between the two

**Consequences to keep in mind while fixing.**
- If the client renders this text as markup rather than text, unvalidated output becomes a rendering and script-injection path as well.

Bound the length, and keep the client rendering the value as text unless it has been sanitised for markup.

### 4. AI-004 — Model call has no explicit bounds (no output token cap; no timeout; no retry, fallback, or error handling) in POST /api/chat

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: ai_app
- **Files**: `src/app/api/chat/route.ts`
- **References**: OWASP Top 10 for LLM Applications: LLM10 Unbounded Consumption; CWE-770 Allocation of Resources Without Limits or Throttling; docs/LIMITATIONS.md — static analysis cannot prove the absence of a defect, and never reports an unmeasured number

**What is wrong.** The call to client.chat.completions.create() sets no explicit bounds: no output token cap, no timeout, no retry, fallback, or error handling. The SDK client is constructed in this module and configures none of them, so the request runs on whichever defaults the installed SDK version happens to ship. Those defaults are not visible in this code and change between versions, which makes the behaviour under a slow or failing provider a property of the dependency rather than a decision the application made. Without an output token cap the length of a response — and therefore its cost and its latency — is set by the model, not by the application. With no retry, fallback, or surrounding error handling, a transient provider error propagates as an unhandled rejection and the caller receives a generic failure. How long a request actually takes and what it actually costs are runtime properties: this analysis reports only which bound is absent, never a figure.

**Why it matters to a user.** A single request can generate a very long response, so users wait on a reply with no ceiling and the provider bill tracks model behaviour rather than product usage. When the provider has a transient failure — which it will — the user sees a server error instead of a retry or a degraded answer, and the request is simply lost. The feature's worst case is therefore unknown to the team until it happens in production.

**Likely root cause.** The first working call was copied from a quickstart example, and quickstarts omit bounds to keep the snippet short.

**Evidence.**
- `src/app/api/chat/route.ts:17`
  ```
  const completion = await client.chat.completions.create({
  ```
  client.chat.completions.create() is called with no output token cap, no timeout, no retry, fallback, or error handling; the SDK client is constructed in this module and sets none of them either

**Consequences to keep in mind while fixing.**
- An upstream slowdown holds server resources for the full default timeout, so one provider incident can exhaust the request pool.
- Without a cap there is no per-request ceiling to reason about when forecasting cost or setting a budget alert.
- A retry added later without idempotency can duplicate side effects performed around the call.

**Recommended remediation.** Set the bounds explicitly at the call site or on the client: an output token cap sized to the longest useful answer, a request timeout shorter than the caller's own deadline (an abort signal so the work stops rather than continuing unobserved), and a bounded retry with exponential backoff and jitter that only retries transient statuses. Wrap the call so a final failure returns a deliberate degraded response — a cached answer, a shorter non-AI path, or an explicit error the UI can render — rather than an unhandled exception. Make the limits configuration rather than literals so they can be tuned without a deploy.

**Estimated effort.** small

**Why it matters to a user.** Users experience quality regressions nobody intended: a reworded prompt that improves one case breaks another, and the first signal is a complaint rather than a failing build. Because the output still looks plausible, bad answers may be acted on before anyone notices.

**Likely root cause.** Model output is not deterministic, so the usual assertion style does not fit and the testing step is skipped rather than adapted.

**Evidence.**

  ```
  const completion = await client.chat.completions.create({
  ```
  prompt and model behaviour are defined here; no test file in the project (1 found) exercises a prompt, and no evaluation harness is configured

2. `src/app/api/chat/route.ts` — the project contains 1 test file(s), none of which names a prompt, a model call, or a golden output
3. `src/app/api/chat/route.ts` — no evaluation harness or golden-output directory exists in the repository

**Consequences to keep in mind while fixing.**

### 6. AI-006 — User-submitted content is sent to the OpenAI API with no redaction and no disclosure in the repository

- **Severity**: medium
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: ai_app
- **Files**: `src/app/api/chat/route.ts`
- **References**: OWASP Top 10 for LLM Applications: LLM02 Sensitive Information Disclosure; NIST AI 600-1 Generative AI Profile (AI Risk Management Framework); GDPR Art. 13 — information to be provided where personal data are collected

**What is wrong.** Text submitted by users is forwarded to the OpenAI API as part of the prompt. Nothing in the project removes, masks, or minimises personal data before that happens, and the repository contains no privacy notice, data-processing document, or documentation stating that user content leaves the system. Whatever a user types — including details they would not expect to be shared, pasted from an email or a document — crosses a trust boundary into a processor the user has not been told about. Whether any particular request actually contains personal data is a runtime property that cannot be determined from the source: this finding reports the absence of both controls, not the presence of a specific disclosure.

**Why it matters to a user.** Users cannot know that their input is processed by an external provider, so they cannot make an informed choice about what to put in it. If the content includes personal or confidential material, it has been disclosed to a third party without notice, which is a problem for the user directly and a compliance exposure for the operator.

**Likely root cause.** The provider call is a technical integration, and the data-protection consequences of it sit with a different part of the organisation.

**Evidence.**
- `src/app/api/chat/route.ts:17`
  ```
  const completion = await client.chat.completions.create({
  ```
  content taken from the request is sent to the OpenAI API by client.chat.completions.create()
- `src/app/api/chat/route.ts:14`
  ```
  export async function POST(req: Request) {
  ```
  the handler starts here: no redaction, masking, or minimisation step appears between this point and the provider call, and no such step was found anywhere in the project

**Consequences to keep in mind while fixing.**
- Data already sent cannot be recalled; the provider's own retention terms govern it.
- A later data-subject deletion request cannot be satisfied for content that left the system unrecorded.
- Enterprise customers commonly require a sub-processor list, which cannot be produced from an undocumented integration.

**Recommended remediation.** Minimise before sending: strip or tokenise identifiers the model does not need, keep prompts to the fields the task requires, and make the redaction step a function the call path must go through rather than a convention. Then make the integration visible: list the provider as a sub-processor in the privacy notice, tell users at the point of input that their text is processed by an external model, check the provider's retention and training settings and record which were chosen, and keep a per-request log of what was sent so a deletion request can be honoured. The affected surface is POST /api/chat.

**Estimated effort.** medium

### 7. AI-007 — Model calls are not instrumented: no token accounting and no AI tracing

- **Severity**: medium
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: ai_app
- **Files**: `src/app/api/chat/route.ts`
- **References**: OWASP Top 10 for LLM Applications: LLM10 Unbounded Consumption; NIST AI 600-1 Generative AI Profile (AI Risk Management Framework); docs/LIMITATIONS.md — static analysis cannot prove the absence of a defect, and never reports an unmeasured number

**What is wrong.** This project issues 1 model call and records nothing about any of them. The usage figures the provider returns with every response are not read, so token consumption is never attributed to a request, a user, or a feature; and no prompt-level tracing tool is present, so the prompt, the model, the parameters, and the output of a given request are not retained anywhere. Nothing here measures runtime behaviour: the gap is that the data needed to measure it is not being collected.

**Why it matters to a user.** When the feature answers badly, slowly, or not at all, there is no record of what was sent or what came back, so the report cannot be reproduced and the user's problem is not fixed. Cost and latency regressions reach users first and the team later, via the bill.

**Likely root cause.** The provider SDK works without any instrumentation, so nothing forces the decision until a cost or quality question is asked.

**Evidence.**
- `src/app/api/chat/route.ts:17`
  ```
  const completion = await client.chat.completions.create({
  ```
  the provider response is consumed without reading its usage figures, and no AI tracing library is present in the project

**Consequences to keep in mind while fixing.**
- Prompt changes cannot be compared against each other without a record of what each one produced.
- Per-customer cost is unknowable, which blocks usage-based pricing and fair-use enforcement.
- An abuse incident leaves no trail showing which caller consumed the quota.

**Recommended remediation.** Record each model call as a structured event: the model and version, the prompt identifier or hash (not necessarily the text), the latency, the usage figures the provider returns, the finish reason, the outcome, and the caller identity. Emit it from one wrapper that every call path goes through, so a new call site cannot be uninstrumented. Add tracing that keeps the prompt and the output for a bounded window — with user content redacted to the project's privacy rules — so a complaint can be reproduced, and alert on error rate, latency, and token consumption per feature.

**Estimated effort.** medium
