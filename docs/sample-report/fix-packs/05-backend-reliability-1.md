### 1. REL-001 — POST /api/webhooks/stripe marks the record settled before reading the payment outcome

- **Severity**: critical
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: reliability
- **Files**: `src/app/api/webhooks/stripe/route.ts`
- **References**: CWE-840 Business Logic Errors; CWE-696 Incorrect Behavior Order

**What is wrong.** In the POST /api/webhooks/stripe handler the record is marked settled at line 19, and the provider's outcome field is not examined until line 24. The write is therefore unconditional: it runs for a failed charge, a cancelled payment, a dispute, and a test event exactly as it runs for a successful one. The branch below can log the failure or alert on it, but the state it would need to prevent has already been committed, and nothing in this handler reverses it.

**Why it matters to a user.** An order whose payment failed is treated as paid: it is fulfilled, shipped, or unlocked, and the customer receives goods or access that was never paid for. The mirror case is just as bad — a customer whose payment genuinely succeeded cannot be distinguished from one whose did not, so support has no reliable answer, and the business discovers the gap through reconciliation rather than through the application.

**Likely root cause.** The handler was written for the success event and later extended with a failure branch, which was appended to the end of the function instead of placed before the state change.

**Evidence.**
- `src/app/api/webhooks/stripe/route.ts:19`
  ```
  data: { status: 'paid' },
  ```
  the record is marked settled here, unconditionally
- `src/app/api/webhooks/stripe/route.ts:24`
  ```
  if (event.type === 'charge.failed') {
  ```
  the provider's outcome is only examined here, after the write above

**Traced relationship** (call):
1. `src/app/api/webhooks/stripe/route.ts:19` (`POST`) — prisma.order.update sets the settled state with no condition on the outcome
2. `src/app/api/webhooks/stripe/route.ts:24` (`POST`) — the success/failure branch is evaluated after the state has already been written

**Consequences to keep in mind while fixing.**
- Revenue reported by the application diverges from the provider's settlement records.
- Fulfilment, entitlement, and email flows triggered by the settled state all fire on failed payments.
- Correcting the data later requires matching every affected record against the provider by hand.

**Recommended remediation.** Read the outcome first and make the state change conditional on it. Branch on the event type or the payment status at the top of the handler, return early for anything that is not a confirmed success, and only then write the settled state — ideally in the same transaction as the idempotency record, so a crash cannot settle a record without logging why. Treat unknown or new event types as "do nothing" rather than as success, and let the provider retry what you did not handle.

### 2. REL-005 — POST /api/webhooks/stripe processes a replayed delivery twice

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: reliability
- **Files**: `src/app/api/webhooks/stripe/route.ts`, `prisma/schema.prisma`
- **References**: CWE-837 Improper Enforcement of a Single, Unique Action; Stripe: Webhooks — handle duplicate events

**What is wrong.** Webhook providers guarantee at-least-once delivery, not exactly-once: a delivery is retried whenever the response is slow, non-2xx, or lost, and the same event id arrives again. This handler records the delivery with prisma.webhookEvent.create() and nothing makes that record unique — there is no read of WebhookEvent by eventId before the write, and the schema puts no unique constraint on the column (declared indexes: id). The duplicate insert therefore succeeds, and every state change in the handler (prisma.order.update) runs a second time. Neither file shows the problem alone: the handler looks like it is recording events, and the schema looks like an ordinary table.

**Why it matters to a user.** A customer can be charged, credited, or fulfilled twice for one real event — the duplicate looks exactly like a legitimate second event, so it is not caught until someone reconciles the books or the customer complains. Refunds and goodwill follow, and the ledger disagrees with the provider's.

**Likely root cause.** The handler was written against a single successful delivery. Retries only appear in production, under exactly the conditions (timeouts, deploys, provider incidents) that make them hardest to notice.

**Evidence.**
- `src/app/api/webhooks/stripe/route.ts:22`
  ```
  await prisma.webhookEvent.create({ data: { eventId: event.id, type: event.type } });
  ```
  the provider's event id is written here with no uniqueness check before the write
- `prisma/schema.prisma:47`
  ```
  eventId   String
  ```
  WebhookEvent.eventId carries no unique constraint, so the database will accept the same event twice
- `src/app/api/webhooks/stripe/route.ts:17`
  ```
  await prisma.order.update({
  ```
  prisma.order.update() in the same handler is repeated on a replayed delivery

**Traced relationship** (webhook_idempotency):
1. `src/app/api/webhooks/stripe/route.ts:13` (`POST`) — POST /api/webhooks/stripe receives provider deliveries
2. `src/app/api/webhooks/stripe/route.ts:17` (`POST`) — changes state via prisma.order.update() before recording the event
3. `src/app/api/webhooks/stripe/route.ts:22` (`POST`) — records the delivery with prisma.webhookEvent.create(), without first checking whether eventId has been seen
4. `prisma/schema.prisma` — WebhookEvent.eventId has no unique index: indexes present are [id]

**Consequences to keep in mind while fixing.**
- Retries cluster during incidents and deploys, so duplicates arrive precisely when the team is already busy.
- Reconciliation against the provider becomes manual, because the local record no longer maps one-to-one onto their events.
- Any downstream consumer of these rows (emails, analytics, accounting) multiplies the error.

**Recommended remediation.** Make the delivery record the idempotency key. Add a unique constraint on WebhookEvent.eventId and insert it *before* doing any work, treating a unique-violation as "already processed" and returning 2xx immediately. Where the ORM supports it, a single conditional insert (`create` caught on unique violation, or `upsert`/`ON CONFLICT DO NOTHING`) is enough. Run the insert and the state change in one transaction so a crash between them cannot leave the event recorded but the work undone. Verifying the provider's signature is a separate and equally necessary control.

### 3. REL-014 — POST /api/webhooks/stripe performs I/O with no error handling

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: reliability
- **Files**: `src/app/api/webhooks/stripe/route.ts`
- **References**: CWE-391 Unchecked Error Condition; CWE-755 Improper Handling of Exceptional Conditions

**What is wrong.** POST /api/webhooks/stripe in src/app/api/webhooks/stripe/route.ts awaits I/O — a database call, a file write, or an external request — and the handler contains no try/catch and no rejection handler. When that I/O fails, and it will (a dropped connection, a constraint violation, a timeout, a provider incident), the rejection propagates out of the handler. The framework turns it into a generic 500 with no application-specific body, no structured log line identifying which operation failed, and no partial cleanup of anything the handler had already changed.

**Why it matters to a user.** The user gets an unexplained failure for something that may be entirely recoverable — a value that needs correcting, a duplicate that already exists, a dependency that is briefly unavailable. Because the response cannot distinguish those cases, the interface cannot tell the user whether to fix their input, retry, or wait, so the usual outcome is an abandoned task and a support request. For a write that partly completed, the user is left not knowing what state their data is in.

**Likely root cause.** The handler was written for the success path. Nothing in the type system or the build requires a failure path, and the framework's default 500 makes the omission invisible until it is examined.

**Evidence.**
- `src/app/api/webhooks/stripe/route.ts:13`
  ```
  export async function POST(req: Request) {
  ```
  POST /api/webhooks/stripe handler contains no try/catch and no .catch()

**Consequences to keep in mind while fixing.**
- Failures are indistinguishable in the logs, so the first step of every investigation is reproducing the request.
- A write that fails halfway leaves the record in an intermediate state that no later code expects.
- Error-rate metrics cannot separate client mistakes from dependency failures.

**Recommended remediation.** Wrap the I/O in try/catch (or a shared handler wrapper, which keeps every route consistent). In the catch: log with enough context to identify the operation and the record, map known failures onto honest status codes (400 for bad input, 404 for missing, 409 for a conflict, 503 for an unavailable dependency), and return a body the interface can act on. Keep internal details out of the response while putting them in the log. Where a handler performs several writes, run them in one transaction so a failure cannot leave the record half-updated.

**Estimated effort.** small

### 6. REL-011 — Promise chain with no rejection handler in OrderSummary.tsx

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: reliability
- **Files**: `src/components/OrderSummary.tsx`
- **References**: CWE-391 Unchecked Error Condition; MDN: Promise rejection handling — unhandledrejection

**What is wrong.** The chain starting at src/components/OrderSummary.tsx:21 attaches success handlers with .then() but never attaches a rejection handler, and the chain is a bare expression statement, so the promise is not returned, awaited, or assigned either. If the request fails — a network error, a non-JSON body, a 500 — the rejection has nowhere to go. It surfaces as an `unhandledrejection` event in the browser, or as an unhandled rejection in Node, where recent versions terminate the process by default. The success handlers simply never run.

**Why it matters to a user.** On failure the component never leaves its initial state: the user sees an empty panel, a spinner that never stops, or stale content, with no error message and nothing to retry. The interface looks like it is still loading forever, so the usual response is to reload and try again, which fails the same way.

**Likely root cause.** The chain was written against the success path. A `.catch()` is easy to omit because nothing warns about it and the happy path works in development, where the request rarely fails.

**Evidence.**
- `src/components/OrderSummary.tsx:21`
  ```
  fetch(`/api/orders/${orderId}`)
  ```
  promise chain started here has no .catch() and no second then() argument

**Consequences to keep in mind while fixing.**
- The failure is invisible to monitoring unless a global handler reports it.
- Any state the chain was supposed to set keeps its initial value, so later code reads it as empty rather than failed.

**Recommended remediation.** Attach a rejection handler that puts the UI or the caller into an explicit error state rather than leaving it in the loading state: `.catch((err) => { report(err); setError(err); })`, and distinguish "loading", "loaded", and "failed" so the render path can tell them apart. Check `response.ok` before parsing, because a 4xx or 5xx does not reject a fetch promise. In new code prefer `await` inside `try/catch`, which makes an unhandled path a visible omission.

**Estimated effort.** trivial
