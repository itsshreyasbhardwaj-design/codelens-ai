### 1. OPS-002 — .github/workflows/deploy.yml deploys on every push to the default branch with no gate

- **Severity**: high
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `.github/workflows/deploy.yml`, `package.json`
- **References**: GitHub — Using environments for deployment; DORA — Deployment automation and recovery capabilities; Twelve-Factor App — V. Build, release, run

**What is wrong.** .github/workflows/deploy.yml is triggered by a push to the default branch and runs a deployment step with nothing between the two: no test step, no lint or type check, no declared deployment environment, no manual approval, no rollback step. The repository does contain a 'test' command, so the verification exists — the pipeline simply does not run it. Every merge therefore becomes a release, and the first place a defect can be caught is production. The absence of a declared environment also means the hosting platform has no opportunity to apply protection rules (required reviewers, wait timers, branch restrictions) to this deployment, and the absence of a rollback step means recovery depends on someone remembering the right command under pressure.

**Why it matters to a user.** Users are the test suite. A change that breaks checkout, login, or any other path goes live within minutes of a merge, stays live until someone notices, and is removed only when a human works out how to undo it — which, without a rollback step, is itself an improvised operation during an incident.

**Likely root cause.** Continuous deployment was set up before continuous integration, which is the easier half to configure.

**Evidence.**
- `.github/workflows/deploy.yml:20`
  ```
  run: npx vercel deploy --prod --token=$VERCEL_TOKEN
  ```
  this step performs the deployment; comments are stripped before matching, so a comment about tests is not a test step
- `.github/workflows/deploy.yml:5`
  ```
  branches: [main]
  ```
  the workflow runs on every push to the default branch, so any merge reaches this deploy step
- `package.json:10`
  ```
  "test": "jest"
  ```
  the project declares 'test' (`jest`), which this pipeline never invokes

**Traced relationship** (import):
1. `.github/workflows/deploy.yml:5` — triggered by push to the default branch
2. `package.json:10` — the project's own 'test' command exists but is not invoked by this workflow
3. `.github/workflows/deploy.yml:20` — the deployment step runs unconditionally

**Consequences to keep in mind while fixing.**
- Mean time to recovery is bounded by how long it takes a human to notice and improvise, not by automation.
- The pipeline provides no record that anything was verified before a given release.
- A broken dependency update or a bad migration reaches production with the same ease as a reviewed change.

**Recommended remediation.** Split verification from release and make the release depend on it: run install, lint or type check, and the test suite in one job, then give the deploy job `needs: [<verification job>]` so a failure stops it. Declare the target environment on the deploy job (`environment: production`) and configure its protection rules — required reviewers and, where useful, a wait timer — in the repository settings, since those rules are not visible in this file. Deploy to a staging environment from the default branch and promote to production from a tag or a manual dispatch. Add an explicit rollback path (redeploy the previous release, or the platform's own rollback command) and record in the repository how to run it.

**Estimated effort.** medium

### 2. OPS-010 — .github/workflows/deploy.yml passes a credential as a command-line argument

- **Severity**: medium
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: devops
- **Files**: `.github/workflows/deploy.yml`
- **References**: GitHub — Security hardening for GitHub Actions; OWASP A05:2021 Security Misconfiguration

**What is wrong.** The value for `VERCEL_TOKEN` is passed as a command-line argument. Arguments are visible in the process table to every other process on the runner, they are captured by shell tracing and by many tools' own error output, and they end up in shell history where a shell is reused. The environment is the narrower channel: it is per-process and is not printed by default.

**Why it matters to a user.** Users are not affected directly. The risk is to them indirectly: a deployment or provider token that leaks into a log reachable by anyone with read access to the pipeline — on a public repository, by anyone at all — can be used to push code or configuration to the service they use.

**Likely root cause.** The documented example for the tool shows the credential as a flag, which is the shortest thing that works.

**Evidence.**
- `.github/workflows/deploy.yml:20`
  ```
  run: npx vercel deploy --prod --token=$VERCEL_TOKEN
  ```
  a secret-shaped value is passed as a command-line argument, where it is visible to other processes on the runner

**Consequences to keep in mind while fixing.**
- A leaked value has to be rotated at the provider; removing the log line does not undo the exposure.
- Forks and pull-request workflows widen who can observe a step's output.

**Recommended remediation.** Give the step an `env:` entry and let the tool read the variable itself rather than receiving it as an argument; most deployment CLIs support an environment variable for their token. Where only a flag is available, pass the value through stdin or a file with restrictive permissions, avoid shell tracing in that step, and replace the long-lived token with a short-lived credential (OIDC federation) where the provider supports it.

**Estimated effort.** small

### 3. OPS-011 — .github/workflows/deploy.yml pins its pipeline steps by mutable tag rather than commit

- **Severity**: low
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `.github/workflows/deploy.yml`
- **References**: GitHub — Security hardening for GitHub Actions; OpenSSF Scorecard — Pinned-Dependencies check; OWASP A08:2021 Software and Data Integrity Failures

**What is wrong.** 2 step reference(s) in this workflow name a tag or branch rather than a commit: actions/checkout@v4, actions/setup-node@v4. A tag is a movable pointer, so the code that runs in the pipeline can change without any change in this repository. These steps execute inside the pipeline with access to its secrets and its checkout, which makes them part of the trust boundary of every release. All of them come from well-known first-party namespaces, which lowers but does not remove the risk.

**Why it matters to a user.** No direct effect in normal operation. If a pipeline step is replaced upstream with hostile code, the consequence for users is a tampered release or stolen deployment credentials, reaching them through the ordinary deployment path and with no local change to point at during the investigation.

**Likely root cause.** Tag references are what every example in the marketplace documentation shows.

**Evidence.**
- `.github/workflows/deploy.yml:11`
  ```
  - uses: actions/checkout@v4
  ```
  `actions/checkout@v4` is referenced by a tag or branch, which the publisher can move to different code at any time
- `.github/workflows/deploy.yml:12`
  ```
  - uses: actions/setup-node@v4
  ```
  also referenced by a mutable tag

**Consequences to keep in mind while fixing.**
- The pipeline is not reproducible: the same commit can run different step code on different days.
- An incident review cannot establish which version of a step ran for a given release.

**Recommended remediation.** Pin each step to a full commit SHA, keeping the tag in a trailing comment for readability, and let an automated update tool raise those SHAs in reviewable pull requests. Give each job the least `permissions:` it needs (start from `contents: read`), avoid exposing secrets to steps that do not need them, and prefer first-party or vendored steps for anything that touches credentials.

**Estimated effort.** small

### 4. OPS-005 — No dependency lockfile is committed, so builds are not reproducible

- **Severity**: medium
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `package.json`
- **References**: SLSA v1.0 — Build track, hermetic and reproducible builds; OpenSSF Scorecard — Pinned-Dependencies check; Twelve-Factor App — V. Build, release, run

**What is wrong.** package.json declares dependencies as version ranges and no lockfile is committed beside it. Each install therefore resolves the whole transitive tree against whatever the registry currently offers, so two builds of the same commit can ship different code — including transitive packages nobody in the project has ever read. A newly published patch version of any dependency, or of any dependency of a dependency, enters the build with no review and no record of the change.

**Why it matters to a user.** Users see breakage that nothing in the repository explains: a deploy of an unchanged commit behaves differently because a dependency moved. In the worst case a compromised package version reaches them through a routine deployment.

**Likely root cause.** The lockfile was never committed, or it was added to .gitignore to avoid merge conflicts.

**Evidence.**
- `package.json:12`
  ```
  "dependencies": {
  ```
  dependency ranges declared here, with no lockfile in the snapshot to resolve them
- `.github/workflows/deploy.yml:15`
  ```
  - run: npm install
  ```
  the pipeline resolves dependency ranges afresh on every run

**Consequences to keep in mind while fixing.**
- A failing build cannot be reproduced locally with certainty.
- Vulnerability scanning cannot state what is actually installed, only what is permitted by the ranges.
- Rebuilding an old commit does not recreate the artefact that was released from it.

**Recommended remediation.** Generate and commit the lockfile for the package manager in use (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `uv.lock`, and so on), then make every automated install honour it exactly (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install --immutable`, `poetry install --sync`). Resolve lockfile merge conflicts by regenerating rather than editing, and let an update tool raise dependency changes in reviewable pull requests.

**Estimated effort.** small

### 5. OPS-007 — No automated dependency update or advisory checking is configured

- **Severity**: low
- **Confidence**: STRONGLY SUPPORTED — evidence is clear but verify the surrounding context
- **Category**: devops
- **Files**: `package.json`
- **References**: OpenSSF Scorecard — Dependency-Update-Tool check; OWASP A08:2021 Software and Data Integrity Failures

**What is wrong.** The project depends on third-party packages and already runs a pipeline, but no dependency update tool (Dependabot, Renovate, or equivalent) is configured and no advisory or vulnerability check runs in CI. Dependency updates therefore happen only when someone remembers, which in practice means a long gap followed by a large, risky upgrade — and a published advisory affecting a direct or transitive dependency produces no signal in this repository at all.

**Why it matters to a user.** Users are exposed for longer to defects and vulnerabilities fixed upstream, because nothing notices the fix exists. When the backlog is eventually cleared, it arrives as one large change, which is itself more likely to break something they rely on.

**Evidence.**
- `package.json:12`
  ```
  "dependencies": {
  ```
  third-party dependencies declared here, with nothing in the repository watching them for updates or advisories
- `.github/workflows/deploy.yml:1`
  ```
  name: deploy
  ```
  an existing pipeline that could run dependency and advisory checks

**Recommended remediation.** Enable an update tool with a schedule and grouping: a `.github/dependabot.yml` or `renovate.json` that batches minor and patch updates into one pull request per ecosystem per week, keeps major versions separate, and is gated by the existing test pipeline so routine updates can be merged on green. Add an advisory check to CI (`npm audit --omit=dev`, `pip-audit`, `osv-scanner`, or the platform's dependency review) and decide which severities fail the build rather than merely reporting.

**Estimated effort.** trivial

### 6. OPS-008 — No error tracking, metrics, or alerting is configured in the repository

- **Severity**: medium
- **Confidence**: SUSPECTED — plausible from the evidence; confirm before changing behaviour
- **Category**: devops
- **Files**: `package.json`
- **References**: CWE-778 Insufficient Logging and Monitoring; Google SRE Workbook — Alerting on SLOs; Twelve-Factor App — XI. Logs

**What is wrong.** No dependency, import, or configuration for error tracking, metrics, tracing, or alerting appears anywhere in this snapshot — not in the manifests, not in the application code, not in the deployment or pipeline configuration. The project therefore has no committed way to learn that something is wrong other than someone looking. Hosting platforms do provide some of this (request logs, basic metrics, crash reporting) and that would not be visible in the repository, which is why this is reported as moderate confidence: the claim is that the repository configures none, not that none exists.

**Why it matters to a user.** Users become the alerting system. A failure affecting a subset of requests — one route, one browser, one payment path — can continue for as long as it takes someone to report it, and because nothing recorded the failure, the report arrives without the detail needed to reproduce it.

**Likely root cause.** Monitoring is usually added after the first incident that could not be explained from logs alone.

**Evidence.**
- `package.json:12`
  ```
  "dependencies": {
  ```
  no error-tracking, metrics, tracing, or alerting dependency or configuration appears anywhere in this snapshot

**Consequences to keep in mind while fixing.**
- There is no error rate or latency baseline, so a regression cannot be distinguished from normal variation.
- Incident investigation depends on logs that may have already rotated away.
- Error budgets and availability targets cannot be stated, let alone enforced.

**Recommended remediation.** Start with error tracking: add an error-reporting SDK to both the server and the browser, capture release and request context, and route alerts to somewhere a human will see them. Then add the few metrics that describe user experience (request rate, error rate, latency percentiles, saturation of any pool or queue) and alert on symptoms rather than causes. Self-hosted and free tiers exist for all of this; the important part is that something other than a user notices first.

**Estimated effort.** medium
