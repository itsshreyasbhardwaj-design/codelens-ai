SEC-001 — SQL built by string interpolation and passed to pool.query()

critical · confirmed confidence · confirmed · priority P0 · detected by static · effort small

What is wrong
The statement passed to pool.query() is assembled by interpolation rather than parameterised. Any value reaching that interpolation is executed as SQL, not treated as data.
User impact
An attacker who controls the interpolated value can read, modify, or delete any data the database user can reach, including other customers' records, and in many configurations can escalate further.
Likely root cause
A query was written as a string because the value was assumed to be internal or already validated.
Evidence
src/lib/db.ts:12

untrusted value interpolated into query text
src/lib/db.ts:13

the built string is passed to pool.query()
Traced relationship
  1. src/lib/db.ts:12 — query text assembled with interpolation
  2. src/lib/db.ts:13 — passed to pool.query() as statement text
Remediation
Replace the interpolation with a parameterised query: pass values as bind parameters ($1/? placeholders or the ORM's tagged-template form such as Prisma's `$queryRaw` with template parameters) so the driver sends them separately from the statement text. Where an identifier (table or column name) genuinely must be dynamic, validate it against a fixed allowlist.
Verification
  • Confirm the query now passes values as bind parameters.
  • Add a regression test that supplies a value containing a quote and a semicolon and asserts it is stored or matched literally.
  • Confirm no remaining call site builds this statement by concatenation.

REL-001 — POST /api/webhooks/stripe marks the record settled before reading the payment outcome

critical · strong confidence · strongly supported · priority P0 · detected by static · effort small

What is wrong
In the POST /api/webhooks/stripe handler the record is marked settled at line 19, and the provider's outcome field is not examined until line 24. The write is therefore unconditional: it runs for a failed charge, a cancelled payment, a dispute, and a test event exactly as it runs for a successful one. The handler was written for the success event and later extended with a failure branch, which was appended to the end of the function instead of placed before the state change.
